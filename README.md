## 快速开始

环境要求：Node.js ≥ 20。

```bash
npm install
npm run dev        # http://localhost:5173
npm run typecheck  # 类型检查（strict）
npm run build      # 类型检查 + 构建到 dist/
npm run preview    # 预览构建产物
```

`dist/` 已是构建产物，需用静态服务器托管（`file://` 下 ES Module 与 IndexedDB 不可用）。

### Windows 一键启动（不想配 PATH）

**最简单：双击 `start.cmd`。** 它会自动找 node/npm（PATH 里没有时回退到 WorkBuddy 托管的 Node，
并把这些目录补进本次会话的 PATH），首次运行还会自动装依赖。跑起来后浏览器打开
http://localhost:5173 。

命令行等价用法：

```powershell
.\start.cmd              # 等同于双击
.\start.ps1              # 直接跑脚本 → http://localhost:5173
.\start.ps1 -Preview     # 构建后跑产物 → http://localhost:4173
.\start.ps1 -Install     # 强制重装依赖
```

> 若 `.\start.ps1` 报「无法加载文件 … 因为在此系统上禁止运行脚本」，这是 Windows 默认的
> 执行策略在拦截。**改用 `.\start.cmd` 即可**：它只对本次运行加执行策略放行参数，不改系统设置。
> `start.cmd` 内部等价于 `启动程序 -ExecutionPolicy Bypass -File .\start.ps1`。

## v0.3 本轮完成内容（科技企业经营）

从个人理财扩展到「创业 + 研发 + 市场」，同时修掉了「鼠标未锁定仍能移动」的输入问题。

### 1. 鼠标锁定输入修复

- 移动条件改为：**未暂停 + 未开面板 + 鼠标已锁定**，三者同时满足才动。
- `keydown` 里的方向键与 `Shift` 采用同一条件；`keyup` 不受限，任何情况下都能清除，按键不会卡住。
- `closePanel` / `resumeFromPause` 恢复前先 `world.clearInput()`：遮罩还挂着时按 `W` 不会让人物走起来。
- 时间照常流逝——这条修复只影响人物操作，不改变「面板不暂停模拟」。

### 2. 创业与经营

- 个人界面 → 「创建科技公司」：自定名称与初始出资（从银行存款真实划出，净资产不变）。
- 公司有独立账户、独立状态与独立报表；企业欠款不追索个人资金。
- 资金操作：追加出资、分红（只能分「现金 − 应付」）、暂停/恢复经营、清算、推进到下一事件。

### 3. 科研高管

三档候选人（能力 5 / 15 / 25，月薪 3,000 / 8,000 / 18,000 元），每人只能被一家公司聘用；
工资按实际任职分钟计提、月末支付，月中解雇不免除已产生的薪酬；没有高管也能用永久积累研发。

### 4. 研发与产品

- 自选研发重点、天数（1–3600）、预算；立项时一次付清，取消不退。
- 90 天内线性增长、90–720 天边际递减、720 天后不再增长（`F(90)=1`、`F(720)=2`）。
- 属性 = `100 × (1 − e^(−原始值/100))`，完全确定，无随机。
- 完成后形成待发布产品：命名、定价、每日营销，然后上市。
- 每个游戏年最多发布一款；发布时赋予不可变代次。

### 5. 市场与代际

- 三类人口群体（50% / 35% / 15%）各有品质偏好；`Q` 为加权品质分数（0–100）。
- 日销量 = `10 × (Q/50)² × 营销系数 × 代际系数`；营销系数 `1 + M/(M+100元)`。
- 每落后一代销量 ×0.5；旧产品**不自动降价、不自动退市**，玩家可主动停售。
- **售价不影响销量**——这是任务规定的简化，不是平衡过的定价模型。

### 6. 三家 AI 公司

天机智算（科技 40）、青屿智能（30）、微澜科技（15），各自有账户、产品、研发与报表；
使用同一套经营逻辑与代际规则，只把决策换成 `features/business-ai` 的纯函数建议。
现金紧张时停售亏损产品、压缩营销；长期危机则清算。市场总览可随时查看它们的状态。

### 7. 存档 v3

`v1 → v2 → v3` 依次迁移：保留个人资金、贷款、股票、就业、时间与位置；玩家没有公司；
三家 AI 从迁移时刻开始经营（不追溯销售、工资与研发），且重复解析同一份旧档不会重复注资。

### 关于草稿与刷新

- 草稿**只在内存里**，不写 `GameState`、不进存档；新游戏 / 读档会清空，避免把上一份进度的输入提交给当前公司。
- 个人财务的月份 / 类别筛选属于**查询状态**（`PersonalUiQuery`），不参与草稿回填，因此不会被旧选择覆盖。
- 结构指纹只看「有哪些区块、产品、报表行、候选人与可选按钮」，不含金额与价格；
  金额变化走原地更新，所以输入框、滚动位置、展开的「计算说明」都不会被重置。
- 结构变化时若焦点还在该栏目的表单里：保留原表单，顶部显示「数据已更新，完成当前输入后自动同步显示」，
  焦点离开后自动补做重建。

## v0.3.1 财务与时间事件修复

本轮只修账务口径与事件顺序，不动玩法参数与界面布局。

| # | 问题 | 修法 |
| --- | --- | --- |
| 1 | 个人流水混入企业与 AI 的经营记录 | 新增 `recentPersonalEntries`（只取至少一端是个人账户的流水）供个人界面使用；`recentBusinessEntries` 按 `companyId` 给企业用；`recentEntries` 语义不变。方向判定改为「钱是否进到个人」：分红是流入、出资是流出 |
| 2 | 高管工资月末才算，权益/可分红偏高；清算会抹掉已发生工资 | 工资改为**按任职分钟持续形成「费用 + 应付」**，月末只做支付；解雇只释放关系、不清负债；清算先付清再分配 |
| 3 | 营销/运营按午夜快照扣一整天 | 改为**费用检查点 + 分钟计提**：只对实际正常经营的分钟计费，日界集中付款；改营销/发布/停售/暂停/分红/清算前先结清 |
| 4 | 月界完成的研发不会停止跳时；再次创业仍识别旧公司 | 核心新增 `shouldStop`，整段（含月结）完成后才判定；停止原因覆盖研发与危机。公司选择统一走 `playerEnterprise` 并排除已清算 |
| 5 | 月初 AI 立项费用落进上月报表 | AI 决策移出日界，统一在「该时刻的日结/月结全部完成之后」执行，同一节点只跑一次 |

### 统一口径

```
工资费用      = Σ 任职分钟 × 月薪 / 每月分钟（整数分，余量留存在任职关系上）
营销/运营费用  = 日预算 × 实际正常经营分钟 / 1440（整数分，余量留存在企业上）
销售成本      = 成交件数 × 锁定单位成本
应付 payables = 工资 + 销售成本 + 营销 + 运营 + v3 遗留
企业权益      = 企业现金 − 应付
可分红        = 现金 − 应付（分红前先结清销售与费用）
```

**费用只在发生时入账一次**：支付只是「现金减少 + 负债减少」，不会再记一次费用；
月报里的费用是发生额，不是付款额。

### 同一时间点的顺序

```
a 个人工资 / 个人利息 / 企业工资与费用应计（按分钟）
b 股票行情
c 日界：销售 → 费用付款 → 危机检查
d 月界：个人月结 → 企业工资付款 → 企业月报（切换当月累计）
e 个人贷款到期
f 研发完成
g AI 决策（每节点一次，且在 c/d 之后）
h 汇总关键事件，决定是否停止本次跳时
```

### 存档 v4

- `v1 → v2 → v3 → v4` 依次迁移，保留公司、资金、研发、产品、人才与历史报告。
- 费用检查点从**旧档当前时间**起算，不追溯估算历史预算。
- 旧档未结算的任职分钟一次性折算成工资转入应付与当月费用；原有应付保留，不覆盖、不重复累计。
- v3 的 `supplyDue` 混合了成本/营销/运营，无法追溯分类：原额保留为「历史经营应付」，
  补付时按经营费用记账，这段历史在报表里无法拆开。
- 同一份旧档重复读取不会再次增加工资或费用；不重建 AI、不重复注资。

## v0.2 完成内容（历史）

### 1. 第三人称与人物

- 摄像机围绕角色做球面环绕：鼠标控制水平/垂直，滚轮调整跟随距离（2.6–9.5 米），  
  俯仰限制 −0.12–1.16 弧度；跟随与缩放都用按时间指数平滑，手感不依赖帧率。
- `WASD` 按摄像机在地面的朝向移动，角色朝实际移动方向平滑转身；**原地转视角不会带动角色**。
- 简单摄像机遮挡：从注视点向摄像机做射线与建筑 AABB 求交，命中就缩短距离，并限制最低离地高度。
- 人物使用公开资源 **RobotExpressive**（作者 Tomás Laulhé / Quaternius，CC0，含骨骼与 Idle/Walking 等 14 个动画）。  
  待机与行走用权重交叉淡化过渡；播放速率按实际移动速度缩放，减少滑步；  
  **撞墙没有实际位移时不播放行走**；位移全部由代码控制，动画不含根位移。
- 加载失败时回退到占位模型，并在控制台明确报错（不影响游戏逻辑）。

### 2. 连续时间

- 时间与移动完全解耦：站立、行走、看面板时都在流逝。

## 时间事件顺序（所有入口一致）

任何时间推进（自然流逝、上班、休息、睡觉）都经过同一个函数 `app/timeAdvance.advanceGameTime`，  
在**一次状态提交**内按固定顺序处理：

```
1. 个人工资应计（本段是工作时）
2. 个人贷款利息计提（按未偿本金、按分钟单利）
3. 企业高管任职分钟累计
4. 行情节点（每 24 游戏分钟一次；跨多个就逐个处理）
5. 日界：各公司当日销售与成本 → 当日营销与运营费 → 补付应付 → 危机检查 → AI 决策
6. 月界：个人月结（原八步）→ 企业工资结算 → 企业月报
7. 个人贷款到期扣款（月界时刻排在月结之后）
8. 研发完成
```

- 内部按 1 分钟粒度分段（核心的语义中性参数 `maxStepMinutes`），因此到期、行情、日界、计息都落在正确节点上。
- 关键事件（玩家研发完成、玩家公司进入资金危机）可在该时刻**提前停止跳时**，并如实返回
  实际推进分钟数、剩余分钟数与停止原因；工作被提前停止时只计已完成工时，不记完整班次。
- 跨越多个行情节点、多个月份都在同一次提交里顺序处理，不逐条重绘、不逐条保存、不逐条弹提示。
- 结算失败整次推进回滚，不会出现「发了工资没扣房租」或「扣了款没更新行情」。

## 净资产

```
企业账面权益 = 企业现金 − 企业应付费用
净资产 = 现金 + 银行存款 + 未发工资 + 股票市值 + 企业账面权益
         − 生活欠款 − 未偿贷款本金 − 已计提未付贷款利息
```

- 借款：资金与负债同增 → 净资产不变。
- 买入股票：资金变持仓（按成交价计入市值）→ 净资产不变。
- 卖出：持仓变资金，已实现盈亏单独记录，不把全部卖出所得当作利润。
- 计提利息：负债增加 → 净资产立即减少（权责发生制）；支付利息只是负债转支出，净资产不再变化。
- 股价变化只影响持仓市值，**不生成任何资金流水**。
- 出资：个人存款变企业现金，只是资产形态转换，净资产不变。
- 分红：企业现金转个人存款，但企业权益同步减少，净资产不变（真正变化的是利润发生的那一刻）。
- 企业权益只计一次，**不会重复把企业现金再加一遍**；已清算公司不计入。
- 企业应付费用计入权益扣减：欠着没付的成本与工资会压低净资产。

## v0.6 政府、选举与动态人口（存档 v11，v12/v13 修正）

本轮在既有经营闭环之外增加一条「城市」主线：人口会自然增长与分层，
市民有政治偏好，城市的最高行政负责人由选举产生，并对企业经营产生真实影响。

### 1) 动态人口

- 初始 10 万人：低 50% / 中 35% / 高 15%；总人口只由三层人数相加得出，不存第二份总数。
- 自然增长每年 +2%，只随游戏时间累计（暂停、后台、关页面都不补算离线增长）。
- 每月结算一次阶层流动：低↔中、中↔高四条路径互不重叠，同一居民不会在同月连升/连降两级，
  流动不改变总人口。
- 经营与股市共同影响流动率：企业就业薪酬、产业发展与经营压力来自**可模拟企业样本**；
  股市普跌会把中产推向低阶层（最多额外 12.25%），高阶层流向中产（最多额外 37.5%）。

### 2) 政治人口与选举

- 四个政治群体（创新发展 / 就业稳定 / 公共服务 / 综合务实），人数由总人口推导，
  **与经济阶层是两套分类，不能相加**。
- 三位候选人：科技与创新、商业与就业、基础设施与城市发展；
  支持率 = 基础认可 + 政策匹配 + 经济评价 + 现任表现 + 竞选宣传（softmax，T = 0.75）。
- 任期 360 游戏日，竞选期 30 游戏日；新游戏在**第 30 天 08:00** 首次投票
  （实际竞选时长 29 个完整游戏日），此后按上一届投票时刻 + 360 天。
- 开局是中性过渡负责人：不享有任何产业政策，也不获得现任竞选加分。
- 零有效票时过渡负责人留任，30 天后重选；实际整数票平票才抽签（独立随机状态，读档不重抽）。

## v0.5.1 存档校验、完整日销量与详情实时刷新（存档 v10）

本轮只修三处缺陷，界面、交易数量求解与产品规则保持不变。

### 1) 即时价格变化不再导致「存档损坏」

行情有两条时间序列：`nextTickMinute` 只表示**下一次定时行情**，而 `history` 还会收到交易、
回购、分红、增发、产品发布等即时价格。旧校验要求
`nextTickMinute === 最后一条历史时间 + 行情间隔`，于是「第 1 分钟成交一笔、第 24 分钟才是定时行情」
的存档会被判成损坏（它要求 25）。

现在分开校验：历史必须严格递增、不得晚于当前游戏时间、最后价格等于现价；
运行中的证券要求 `当前时间 < nextTickMinute ≤ 当前时间 + 一个行情间隔`；
已终止证券或已清算公司不再要求调度追赶当前时间。`adjustPrice` 仍未改动，
即时价格事件不会重排定时行情，也不会删除任何真实价格历史。

### 2) 只有覆盖完整游戏日的销量才参与估值

产品新增 `dailyObservationStartMinute`（观察起点）：
- 正式发布时重置为当前分钟，并把销量快照对齐累计销量；开局已有产品从开局时刻起算；
- 日界先由统一销售结算结清，再判断「观察起点 ≤ 日界 − 一天」；
  覆盖完整日才写入一条日销量样本，否则**只**推进快照与观察起点（半天的量不冒充一天）；
- 因此 23:59 发布的产品，第一个午夜不会留下「一天零销量」的负面样本，
  要等到下一个完整日才记录；暂停/停售后的完整日零销量仍是有效样本；
- 没有完整日样本时销量因子保持 1，不折算、不猜测。

### 3) 输入交易数量时，公司详情与饼图实时更新

`patchLive`（输入框有焦点或鼠标按下时走的局部刷新）现在同时刷新
`[data-el="company-detail"]`：价格与公司状态、总发行股份、在售/未在售数量与百分比、
库存股、做市库存、愿售比例、玩家持股，以及饼图弧段、中心文字和图例。
数据与交易预览来自**同一次**只读视图（同一时刻、同一证券）；只替换这个不含输入框的区块，
不重建面板、不打断输入焦点与滚动。

### 存档 v10

v9 → v10 只做一件事：**重建短期销量观察窗口**。
`dailySales` 清空、`daySnapshotUnits` 对齐当前累计销量、`dailyObservationStartMinute` 设为存档当前时间。
产品的累计销量、收入、成本、属性、发布时刻、首发股价影响，以及企业财务、资金、股权、

### 产品属性影响股价（一次性发布反应 + 有界销量因子）

两项规则都只走统一的行情接口，都只对**上市公司**生效，且都不改销量模型。

**1) 首次发布的一次性反应**（`app/securities-settlement.applyProductReleaseImpact`）

```
A =（performance + reliability + usability）÷ 3     ← 等权平均，与销量口径 Q 不同
t = clamp((P − 100) ÷ 900, 0, 1)                     ← P 为发布前股价（元）
U = 20 + 60 × t        L = U ÷ 2
A > U  → +0.25% × (A − U)，上限 +5%
A < L  → −0.25% × (L − A)，下限 −5%
L ≤ A ≤ U → 0%（不产生额外影响，但正常行情照常走）
```

玩家命令与 AI 决策共用这个入口，与发布在同一次状态提交内完成。
`Product.releaseImpactPct` 一旦写入（含 0）就不再计算，所以重复点击、刷新、读档、日结
都不会二次施加；未上市公司不创建证券，也不补发历史奖励；旧档已发布的产品标记为「已结算」。

**2) 有界销量因子**（`salesPerformanceFactorOf`）

```
s    = clamp(最近 3 个完整游戏日的日均实际日销 ÷ PRODUCT_MARKET.baseDailyUnits − 1, −1, 1)
因子 = 1 + 10% × s
```

日销量由统一销售结算在日界用 `totalUnits` 增量记录（只保留 5 条，同一天取较大值，
不会重复累计）。因子直接乘在**估值锚点**上，不做逐日连乘，因此不会复利叠加；
没有完整日记录时返回 1。产品停售后窗口自然衰减到 0 销量（因子 0.9），
发布下一款后自动改为观察新产品，旧产品销量仍正常进企业财务。

### 公司详情：在售 / 未在售 / 库存股

证券中心右栏新增「公司详情 · 股份供给」：公司名与现价、总发行股份、

  它只改「挂出多少」，不转移股份、不创造资金、不增发、不自动卖任何人的持仓。

### 第二轮验收修复

- **宣传强度**：`strength` 是公式小数，读档校验改为「有限、非负、≤ 12%」，失败记录必须为 0；
  金额与时间仍按整数校验。正常宣传后保存不再导致读档失败。
- **外部股东提案不再永不触发**：日界判断改用统一日历（`minuteOfDay === 0`）与日历日序号，
  不再依赖「累计分钟整除 1440」；同一日界只检查一次，月界时排在月结之后。
- **旧 v6 公司补齐股权簿**：v6→v7 与 v7→v8 都走同一个幂等补建函数；
  已保存的 v7 档里缺簿的玩家公司同样恢复为「100% 玩家、未上市、无新增融资」。
- **预留不再被永久锁住**：报价 id 全局唯一（含申请标识）；作废报价按自己的单据释放；
  v6 遗留的整体 `legacy` 预留在一轮报价作废后释放；`releaseFunds` 不再跨单据补扣。
- **回购需要本次确认**：输入股数后显示请求量、可成交量、含冲击均价、总额、价格影响与不可执行原因，
  确认框用同一份数字；执行时重校验，数量或价格变化即拒绝（不缩量、不换价）。
- **卖出可成交股数求解（精确版）**：卖出仍在「本次请求量、实际持股、单笔上限」这三重上限内求解，
  但不再依赖「付不起就一定更付不起」的单调假设——取整会让总额在档位边界回落。
  改为按成交价档位求解（同档内总额严格递增、档起点金额沿股数单调），先定位最后一个付得起的档，
  再在档内取 `min(档末, 预算 ÷ 档价)`，得到的是区间内真正可支付的最大整数股数；
  买入侧保持原有单调二分（其单调性可证明）。
- **零持股 CEO 可被罢免**：`remove-ceo` 只校验目标是现任 CEO 且身份合法，不要求其持股；
  「卖光股份即撤职」仍然不做。

## 已知限制

1. 每月固定 30 天、每天 24 小时，不模拟真实月长、星期、节假日。
2. 1 倍速下一个游戏月需要 5 小时现实时间；验收跨月请用住宅面板的「休息 7 天 / 1 天 / 睡到明早」。
3. 证券中心的交易是「做市商报价 + 有限库存/资金」的简化模型：没有挂单簿、做空、手续费与竞价撮合；
   做市库存有限，库存为 0 时买不进去（需要有人先卖）。
4. 贷款同时只有一份合同，不自动续贷、不借新还旧、不加罚息、不触发破产。
5. 利息按支付时点计入月报支出（现金流口径），跨月计提与支付可能不在同一个月报里。
6. 建筑模型未精调门面朝向；人物模型朝向按 glTF 惯例假定为 +Z（若发现倒退走，调 `PLAYER.model.yawOffset`）。
7. 存档在浏览器本地；跨设备用 JSON 导入导出。
8. 未实现跑步、跳跃、战斗、室内、车辆、房地产、政府项目与并购；企业股权融资、多公司上市、
   股东表决与回购已在 v0.4 实现，规则见上文与 `docs/contracts.md` 第十五节。
9. **市场是抽象模型，定价没有做过经济平衡**：售价完全不影响销量，也没有竞争份额、
   供货上限与消费者预算，因此「定高价 + 高销量」可以获得很高的利润。这是任务规定的简化，
   不是可玩性结论。
10. 一家公司同时只有一个研发项目、一个科研高管；研发预算一次付清，无预付款与分期。
11. 每个游戏年（360 天）只能发布一款产品，跨年需要等时间自然流逝。
12. AI 只做「停售亏损品 / 压缩营销 / 立项 / 发布 / 长期危机清算」，以及资金紧张时申请融资、
    拿到报价后按缺口与稀释程度选择接受或全部拒绝；不做价格搜索、并购与上市承销。
13. 企业危机只按「是否还有未付应付」判定，没有宽限期，也不区分欠款性质。
14. 旧产品不自动降价、不自动退市，长期在售会持续占用每日营销预算。
15. 营销与运营费只在检查点（日界 / 月界 / 相关操作）入账，两次检查点之间界面上看不到这段时间的费用，
    权益会略偏乐观，下一个检查点补齐。
16. v3 及更早存档里的「历史经营应付」无法再拆分成本/营销/运营，迁移后统一按经营费用补付。
17. K 线从 v5 起积累：读旧档后图表从当前时刻重新开始，不补齐历史；首根蜡烛通常只有约 4 次更新。
18. 界面状态（栏目、分页、筛选、浮窗位置）只在内存里，刷新页面后回到默认；股票浮窗不写进存档。
19. 本轮不做移动端适配，小屏下窗口会压缩到可用区域但不保证理想排版。
20. 草稿与窗口位置都只在内存里：刷新浏览器页面会回到默认，不会恢复上次的未提交输入。
21. 结构变化被推迟更新时，该栏目会短暂显示旧数字（顶部有黄色提示），焦点离开后才刷新。
22. 旧存档里没有写入过官方名称，改名不影响读档；但历史流水的备注文字是当时生成的原文，不做追溯替换。
