# 模型与动作开发工具：讨论与规划

状态：讨论稿（2026-10-31 起），保留需求、限制和讨论记录。工具已实现（2026-10-31）；2026-11-01 两轮完成了 GLB 内嵌贴图修复、资源状态判定、角色静态朝向/连续转向、外部贴图与资源负例、RoundCuboid 自检和软件渲染验证。**现行命令、参数、结果契约与实测范围以 `tools/model-tool/README.md` 和 `model-tool-architecture.md` 为准**，本文不再复述可运行细节。后续讨论形成的新想法、决定、限制和待验证项继续更新在本文。当前人物任务另见 `character-animation-plan.md`；工作包见 `model-tool-work-packages.md`。

## 目标

为未来不同的 AI Agent 和开发者提供项目内可发现、可复现的无头工具，帮助检查、预览和处理人物及其他 3D 模型，减少每次手工操作和重复编写脚本。玩家正常启动游戏时不需要看到开发工具。

工具应尽量复用游戏实际使用的 Three.js 加载、材质与动作逻辑，减少预览与游戏呈现不一致；但工具预览成功不等于实际游戏体验或性能通过。

## 长期方向：面向 Agent 的无头开发

用户希望游戏内核未来逐步发展为微型游戏引擎，并具备方便不同 Agent 使用的无头开发能力。本节是长期方向，不代表本轮要改造引擎、实现完整编辑器或预建通用框架。

衡量重点是 Agent 能否独立完成“发现能力 → 理解输入 → 检查资源 → 执行有限修改 → 查看报告与截图 → 决定下一步”，而不是仅有人类可操作的界面。先围绕模型和动作验证实际工作流，再根据真实需要考虑场景、资源和其他引擎能力。

方便 Agent 使用的设计目标：

- **容易发现**：实现后在 `AGENTS.md` 中提供简短入口；工具本身提供 `--help`、能力清单和具体示例。未安装或不支持的能力应明确报告。
- **容易调用**：非交互命令接受明确的文件路径、参数和输出位置；无需依赖窗口焦点或手动操作。实际命令和参数在实现并验证后再写入本文。
- **结果可理解**：输出有版本的结构化报告，包含成功/失败、诊断、警告、统计数据和生成文件路径；采用明确退出码。截图与 JSON 结果可对应，便于 Agent 查看。
- **可复现**：记录输入、工具/渲染版本、关键参数、动作时间点和相机设置；截图输出不能替代实际游戏验收。
- **安全迭代**：原始资产默认只读，修改输出到明确的派生路径；覆盖已有文件需明确授权或保护。对批量修改提供可先检查拟变更的方式，具体机制在实现时确定。
- **清楚的能力边界**：分别报告格式的读取、截图、动作处理、写出与已知限制；错误应包含可行动的原因，不能静默降级后宣称成功。
- **成本可控**：纯数据检查与截图分开；Agent 先检查再决定是否渲染，尊重用户规定的启动次数和测试预算。

举例：Agent 收到“检查 Alina 能否制作跳跃动作”，先调用资源检查并读取动作和骨骼报告，再在批准的运行预算内生成关键帧截图，最后报告可用动作、缺口和不确定性；只有得到相应任务授权后才生成派生资产。该流程现已有对应命令（`inspect` / `snapshot` / `retarget` / `animation-edit`），但每步的**实测范围**仍以 README 为准，示例本身不代表动作可用性已验证。

## 用户已表达的方向

- 工具由 Agent 通过命令行或等价的非交互方式使用，无须人工打开游戏窗口。
- 支持对模型及动画生成截图，供 Agent 查看、比较和讨论；同时输出可供程序读取的结构化报告。
- 未来可能处理多种人物、建筑、家具等模型；优先考虑现有 GLB/glTF 和 Alina 的 USDZ，具体格式能力需逐项验证。
- 可以逐步支持动作检查、裁剪、映射和其他修改；不能假设所有格式都能无损编辑或写回。
- 原始模型默认只读；处理结果写入新的派生文件并记录来源，不能静默覆盖原始资产。
- 工具、文档与帮助信息应让后续不同 Agent 可以独立发现并使用，不依赖当前对话。

## 用户指定的首批目标（2026-10-31 指定；部分已实现）

用户希望首批覆盖：模型检查和处理；动作查看和修改；动作处理辅助；将已有动作套用到其他模型；比例与位置校准；碰撞可视化；资源检查报告。以下区分“已实现/受限”与“仍是目标”。

- **模型检查和处理**：先定义实际需支持的检查和可逆处理，格式分别列出可读、可处理、可导出的能力，保留原始模型。
- **动作查看和修改、处理辅助**：优先列出、截图预览和检查已有片段，裁剪、重命名、循环处理及导出需逐项验证；复杂动作生成和蒙皮修复不保证自动完成。
- **已有动作套用到其他模型**：评估骨骼映射、绑定姿态、身高比例、方向、根运动和目标蒙皮；输出映射、未匹配项及前后关键帧。自动映射只能作为候选，需检查实际效果及动画许可，不能承诺任意人物一键兼容。
- **比例与位置校准**：报告原始包围盒与单位，生成带地面、标尺和门洞等参照的截图；明确区分仅改变游戏表现配置与写出派生资产，不擅自改变世界尺度或物理碰撞。
- **碰撞可视化**：从项目真实物理数据展示人物胶囊及场景碰撞，优先截图/报告；资源预览中没有实际场景物理数据时明确说明，不能把模型包围盒误称为游戏碰撞。
- **资源检查报告**：输出有版本的机器可读结果及易读摘要，包含来源、模型和动作、资源引用、问题与输出路径；检查许可的信息来源及未知项，不自动判定权利有效。

### 是否能帮助 Agent：需要实证

检查、结构化报告和可复现截图有望减少重复探索并改善定位，但收益取决于输出正确、命令易发现、依赖易安装，以及不同格式的真实兼容性。动作重定向、编辑和碰撞尤其不能仅凭工具存在就宣称准确或自然。

在扩大实现前，用 Alina、现有 `Casual_Male.glb` 及一个实际场景作为候选试点（具体用例及运行预算由用户批准），比较没有工具和使用工具时的完成步骤、人工介入、错误及处理时间；核对报告与截图是否与游戏真实加载和物理数据一致。记录失败、误报、人工修正和未验证项，不把一次成功视为通用保证。性能和动作手感需独立验证，不以截图代替。

实施建议按依赖分阶段交付：先建立只读检查、报告和截图，再在核验基础上做受控派生编辑及动作重定向，碰撞接入现有物理数据独立验证。功能拆分和验收标准由架构设计与用户确认；“已实现”不等于验收通过，当前限制见 README。

### 实际案例：角色转向后四肢动作方向异常

用户发现 Alina 仅朝特定方向移动时手脚动作正常，其他方向似乎沿固定方向摆动。实施方的定位是：此前程序化动作绕固定世界 X/Z 轴旋转，人物转身后四肢未随角色局部轴转动；当前源码改为从角色 `inner` 世界四元数计算局部轴，Player 先更新角色朝向再更新动画。这是实施方报告的结论；修复后的多方向实际效果仍需独立验证，不能仅凭说明宣称问题已消除。

建议工具将来支持对同一模型、同一动作、同一关键帧，以角色朝向 0°、90°、180°、270°生成可复现的截图或对比图，并可检查连续转向过程；相机视角、时间点、坐标轴和模型/骨骼变换需明确记录。除视觉对照外，可报告相对于角色局部坐标的骨骼或关节点方向，辅助发现世界轴误用、父级矩阵滞后和姿态翻转。

动作方向检查应复用游戏实际的角色动画和变换流程。不同朝向的动作应相对于人物身体保持一致；但静态截图和数值指标不能单独证明动作自然、转身过程平滑或游戏中完全正常。截图需后台渲染并遵守当次任务的运行预算；不自动结束已有游戏进程或使用生产存档。

为自动防止同类问题，工具设计应满足：

- 对程序化姿态、动作重定向和方向变换明确记录坐标空间（世界、角色局部、骨骼局部）、模型前向/向上轴和绑定姿态；按角色及骨骼实际父级变换计算，不把世界 X/Z 固定当作角色前后/左右。
- 操作前更新必要的父级世界矩阵，明确变换顺序；对未知轴约定、镜像、非均匀缩放或无法可靠转换的骨架输出诊断并停止相关自动修改或要求明确参数，不静默猜测。
- 对相同动作相同时间点在多个角色朝向下比较相对角色坐标的骨骼姿态或关节点方向，结合四方向截图定位差异；对转向中的连续帧单独检查，给出可复现参数和异常，而非针对特定角度写反向补丁。
- 该检查是拟议的自动防护，不保证发现所有骨骼、蒙皮或视觉问题；实现后需用包含已知方向问题的案例验证，成功和失败均记录。资源来源和实际游戏运行路径不同也可能产生差异。

## 运行和输出原则

- 纯数据检查不需要启动游戏；无头截图仍需启动后台渲染进程，可能依赖 Chromium、WebGL、GPU 或软件渲染，须记录使用的运行环境和失败原因。
- 无头截图应记录模型及版本、动作、时间点、相机、背景、渲染环境和输出文件，方便 Agent 复现；结构化报告使用可版本化的稳定格式，精确字段待实现时确定。
- 单张截图不能证明动作流畅、物理碰撞正确或性能达标；未运行的事项标记为未验证。
- 任一格式须分别说明读取、动画预览、修改和导出能力；USDZ 可以被加载不代表可无损写回。
- 资源及派生动作应记录来源、作者、许可、署名、修改及再分发状态；不绕过素材授权要求。
- 工具不得向正式玩家页面暴露任意文件读写、系统命令或开发者权限。执行范围和输出路径应明确，避免覆盖用户数据。
- 遵守 `AGENTS.md` 的最小测试要求与当前任务的更严格限制。Alina 本轮游戏启动最多三次；无头渲染如何计入该预算尚待用户决定，不能自行假定已经获准。

## 其他无头开发能力候选（讨论中）

以下不是已授权的实现清单，也不改变现有业务和物理契约。优先级按当前项目的潜在价值判断，需在真正实施前按具体问题重新确认。

| 候选 | 可能提供的能力 | 建议优先级与边界 |
| --- | --- | --- |
| 资源清单与引用检查 | 列出模型、贴图、大小、引用和缺失文件；辅助检查打包遗漏及资源来源记录 | 较高；优先只读，静态结果不能保证运行时全部加载成功 |
| 场景与比例快照 | 按位置或预设视角输出截图与场景对象、包围盒、尺寸；辅助检查人物、门洞和家具比例 | 较高；截图需渲染进程，不能替代游戏手感验收 |
| 碰撞与导航诊断 | 导出或叠加可视化地面、墙、门洞、人物胶囊和碰撞盒，检查明显重叠或通道受阻 | 较高；使用现有 Rapier 和碰撞数据，不能另建第二套权威物理规则 |
| 存档安全检查 | 离线检查快照格式、版本、迁移和现有校验结果，输出字段级可理解诊断 | 较高；默认只读、仅处理明确提供的副本，不自动修复或覆盖玩家数据 |
| 场景布局检查 | 查看街区、建筑、道路及室内布置的数据和基本边界冲突 | 按实际建设需要；只调用现有规划规则，不另造业务事实或自动改布局 |
| 运行日志与故障报告 | 收集明确范围的资源加载错误、崩溃、关键配置及版本，输出便于复现的摘要 | 按需；避免采集不必要的用户数据，并说明日志位置与保留方式 |
| 指定操作的最小冒烟脚本 | 对当前变更执行可重复的单一关键操作并记录结果 | 按需；需要运行时要计入当次任务预算，不扩建大规模自动游玩 |
| 性能观察 | 在明确设备、场景、分辨率下记录加载时间、帧时间等样本 | 后续按具体性能问题实施；标注环境与差异，不能从单次截图推断表现 |
| 地图/资源修改预览 | 对受限数据生成变更计划、前后差异和截图；获授权后写入派生结果 | 后续候选；默认只读预览，保留原始数据，不自动修改存档或游戏规则 |

与模型工具一样，各能力应提供明确帮助、版本化机器可读报告和有意义的失败信息。能复用现有项目校验、场景与物理实现时优先复用，不复制第二套规则；不能安全导入游戏模块时先报告耦合和最小方案。

## 原建议实施顺序（现按工作包设计）

1. 最小原型：对 Alina 读取并输出模型、骨骼和动作报告；无头渲染指定动作的关键帧截图。
2. 通过实际模型验证可靠性、渲染限制和输出是否可供 Agent 理解；再决定是否加入动作映射和裁剪。
3. 基于真实需求逐步考虑骨骼重定向、姿态编辑、批量处理和动画组合；复杂动作与蒙皮修复可能仍需专业工具和人工审看。

当前架构选择和目标命令见 `model-tool-architecture.md`；是否使用 Blender 等外部工具仍未确定。不得仅凭讨论文档引入依赖或修改游戏架构。
