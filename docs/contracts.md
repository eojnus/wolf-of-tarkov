# 公共接口与规则契约

本文件记录**当前**规则：每条规则只保留一份说明，描述的是真实接口与真实约束
（不是某一轮的临时约定，也不用「签名以代码为准」来回避过时描述）。
带版本号的章节描述该字段/接口的存档形态与迁移口径。

## 一、时间

### 唯一时间源

- 只有 `ClockState.totalMinute`，**整数游戏分钟**，从游戏起点（默认第 1 年 1 月 1 日 08:00）起算。
- 日历简化：每月固定 30 天、每天 1440 分钟；不模拟真实月长与节假日。
- 任何代码都不得直接写 `clock.totalMinute`，只能通过 `advanceClock` / `advanceGameTime` 推进。

### 流速

- 正常速度：`minutesPerRealSecond = 2.4`（现实 1 秒 = 游戏 2.4 分钟，600 秒 = 24 小时，10 分钟 = 1 天）。
- 倍率 ∈ {1, 2, 4}，**同时作用于时间与行情**；不影响人物移动与动画速度。
- 主循环按真实 dt 累积小数分钟，取整后提交，**余量保留**，因此正常帧波动不会持续丢时间。
- 位移有单帧上限（`maxMoveDeltaMs = 100`），该上限**只用于移动**，不用于模拟时钟。
  模拟时钟另有 `maxSimDeltaMs = 1000` 的极端保护，常规帧远小于它。

### 暂停

- 有效暂停 = 手动暂停 ∨ 暂停菜单打开 ∨ 页面隐藏。
- **业务面板打开不暂停模拟**，只锁定人物操作并释放鼠标。
- 页面隐藏时暂停并把时间余量与帧基准清零；返回后从原游戏时间继续，不补算后台时间。
- 关闭游戏不计算离线时间、离线行情或离线收益。

### 推进接口

```ts
advanceClock(clock, minutes, cfg, hooks?, options?: { maxStepMinutes?: number }): AdvanceOutcome
advanceGameTime(draft: GameState, minutes: number, options?: { job?: JobConfig | null }): AdvanceResult
```

保证：

1. 一次推进若跨越 N 个月界，`onMonthEnd` 按时间顺序调用 N 次，不跳过、不合并。
2. 每个 `onElapsed` 段都落在同一月份内；段内用 `startMinute` 判定归属月份是安全的。
3. 到边界那次推进，**先** `onElapsed`（工资与利息计入），**后** `onMonthEnd`（结算）。
4. `advanceGameTime` 固定以 1 分钟为分段粒度，因此行情节点与到期时刻都落在正确位置。

## 二、时间事件顺序（所有入口一致）

`app/timeAdvance` 在**一次提交**内按下列顺序处理，任何入口都不得改变：

| 顺序 | 事件 | 触发位置 |
| --- | --- | --- |
| 1 | 工资应计（仅当本段是工作） | 每个 1 分钟段 |
| 2 | 贷款利息计提（未结清、有未偿本金时） | 每个 1 分钟段 |
| 3 | 行情节点推进（跨几个处理几个） | 每个 1 分钟段 |
| 4 | 贷款到期扣款 | 段末，且**不是**月界时 |
| 5 | 月度结算（八步） | 月界 |
| 6 | 贷款到期扣款 | 月界，**必须在月结之后** |

- 跨越多个月份时逐月重复 5–6。
- 多个行情节点在同一次提交内逐个计算，不逐条重绘、不逐条保存、不逐条弹提示。

## 三、资金

### 单位与范围

- 一律「分」为单位的整数；进入业务前必须通过 `assertMoneyRange`。
- 单笔上限 1e12 分；余额必须是非负安全整数。

### 账户

```ts
type AccountOwner = 'personal' | 'business' | 'investor' | 'market' | 'external'
interface AccountRef { readonly owner: AccountOwner; readonly id: string }
```

- `personal` / `business` / `investor` / `market` / `household` 是有真实余额的资金主体；
  `external` 只表示无余额的系统外部对手方。
- `household` 是宏观居民群组账户（id = 群组 id），余额在 `subjectAccounts['household:<id>']`；
  它没有资金预留语义（预留只属于 `investor` / `market`）。
- 个人只有 `personal.cash` 与 `personal.savings`；外部对手方 id 包括 `employer` / `landlord` /
  `utilities` / `creditor` / `opening` / `market` / `lender` / `customer` / `supplier` / `staff` /
  `advertiser` / `operator` / `investor` / `tax`。

### 写接口

| 函数 | 语义 | 失败方式 |
| --- | --- | --- |
| `receiveIncome` | 外部 → 现金（工资） | 抛错 |
| `receiveToSavings` | 外部 → 存款（贷款放款、股票卖出） | 抛错 |
| `payFromPersonal` | 个人 → 外部，现金优先、存款补足 | 不抛错，返回 `shortfall` |
| `payFromSavings` | 个人 → 外部，只用存款（股票买入、贷款还款） | 不抛错，返回 `shortfall` |
| `transferCashToSavings` / `transferSavingsToCash` | 账户内部转移 | 抛错 |

- 余额只能通过这些函数变更；一次支付可能拆成 1–2 条 posting，共享 `operationId`。
- 同一 `operationId` 重复提交被拒绝（`DUPLICATE_OPERATION`）。

### 业务类别与收支口径

| 类别 | 计入月报收支 |
| --- | --- |
| `salary` / `rent` / `living` / `debt-repayment` / `loan-interest` | 是 |
| `initial` / `deposit` / `withdrawal` | 否（开局与内部转移） |
| `stock-buy` / `stock-sell` / `loan-drawdown` / `loan-principal` | 否（资产 / 负债形态转换） |
| `home-purchase` / `home-sale` / `land-purchase` / `land-sale` | 否（资金 ↔ 物业形态转换） |
| `housing-income` / `housing-consumption` | 否（宏观居民收支，个人月报不涉及） |

## 四、业务接口

### stock

- `advanceMarket(market, upToMinute)`：把行情推进到该时刻（含），跨越多个节点则逐个处理。
  返回更新次数。**只依赖 `nextTickMinute` 与 PRNG 状态**，因此分段推进与一次推进结果相同。
- 每次更新：`pct ∈ [−maxChangePct, +maxChangePct]` 均匀分布、零趋势；
  `price = max(1, round(price × (1 + pct)))`；历史按 `historyLimit` 截断。
- `previewTrade(state, securityId, side, requestedShares)`：统一只读预览，按请求量、玩家存款或持股、
  做市在售库存或现金、单笔上限计算可成交股数、含冲击均价与总额；具体预算求解见「资本契约」。
- `GameCommands.buyStock / sellStock(securityId, shares, expectedPriceCents)`：玩家命令入口，
  重新预览并要求请求量全部可成交，不缩量；界面确认的均价作为 `expectedPriceCents` 传入。
- `executeTrade(state, input)`：唯一成交入口，再次计算预览并核对数量与确认均价；在同一次提交内完成
  资金划转、股权簿转让、证券持仓兼容股数同步、成本与成交笔数更新、行情冲击。买入从个人**存款**付款，
  卖出款进个人**存款**；卖出按比例结转成本，差额计入 `realizedPnl`。
- 持仓成本以「总成本（分）」保存，平均成本展示时计算，避免逐股取整误差。

### loan

- `borrow(state, finance, amount, ctx)`：无未结清合同时才可借；放款进存款；`dueMinute = atMinute + 30 × 1440`。
- `accrueInterest(state, minutes)`：`numerator += outstanding × minutes`，
  `interest = floor(numerator / 4_320_000)`，余量保留在 `interestNumerator`。
  **调用方保证每段时间只调用一次**，否则会重复计提。
- `repay(state, finance, amount, ctx)`：先息后本，只能用存款；超付 / 存款不足 / 无合同均抛错。
- `settleDue(state, finance, ctx, nowMinute)`：仅当 `status === 'active'` 且已到期时执行一次，
  尽力偿还，未结清则置 `overdue`；不会重复扣款。
- 逾期继续计息，不加罚息、不自动续贷、不借新还旧。

### employment / living / banking

保持 v0.1 语义不变。`accrueWork` 只在新的一天开始时整理工时记录，避免按分钟调用时反复排序。

## 五、月度结算

八步顺序（`app/monthly.ts`），不变（房租按 `app/residence.monthChargeOf` 报价，
永久居住权为 0）：

1. 结清上月工资应计 → 2. 发薪到现金 → 3. 偿还旧生活欠款 → 4. 扣房租 → 5. 扣生活费 →
6. 差额分别记生活欠款 → 7. 生成月报 → 8. 记录已结算月份。

- 整段运行在 `store.run(draft)` 内，任一步抛错全体回滚。
- 同月不可重复结算（`settledMonths` + `operationId` 双保险）。
- 贷款到期扣款**不在**月结内部，而在月结之后由 `timeAdvance` 触发，保证「先发薪与生活费用、再还贷」。
- 贷款利息与生活欠款是两种负债，分开管理，不互相冲抵。

## 六、存档

### 结构（v2）

```ts
interface SaveSnapshot {
  format: 'city-wealth-sim'
  version: 2
  savedAt: string
  reason: 'manual' | 'auto' | 'import'
  migratedFrom?: number        // 仅迁移时存在，不写回文件
  state: GameState & { world: WorldSaveData }
}
```

新增切片：`market`（价格、下次更新、PRNG 状态、历史、计数）、`stock`（股数、总成本、已实现盈亏、成交笔数）、
`loan`（合同或 `null`）。`world` 增加可选 `camera`。

### 迁移（v1 → v2）

- 保留：资金、流水、就业与工资应计、生活欠款、已结算月份、月报、设置、玩家位置、游戏时间。
- 新增：行情按 `initialPriceCents` 从**迁移时刻**起算（`nextTickMinute = now + tickMinutes`），不追溯历史；
  持仓为空；无贷款。
- 旧存档的时间流速直接切到新规则（没有额外字段需要改）。
- 版本高于当前：拒绝并提示，不覆盖当前游戏。

### 校验

- 校验器逐字段检查，包括：股价 ≥ 1 分、PRNG 状态 ≤ 2³²−1、行情历史非空且不超上限、
  各金额非负且为安全整数、已实现盈亏为整数（可负）、贷款状态枚举、摄像机数值有限。
- 读档顺序：解析 → 迁移 → 校验 → **整体替换**；任一失败都不改动当前进度。
- 槽位保留上一份有效快照（`<slot>-prev`），当前快照损坏时回退并明确提示。

## 七、表现层契约

- `ui` / `world` 只通过 `GameViewModel` 读取数据，字段均为已格式化的只读值。
- 写操作只有 `GameCommands` 的公开方法。
- 建筑只通过 `BuildingConfig` 的稳定 `id` / `interactionId` 参与逻辑；模型文件名、节点名、
  材质、动画名都不参与业务判断。
- 人物模型只影响表现：加载失败回退占位模型，业务逻辑不知情。

## 八、企业资金契约（v0.3）

### 账户

- 企业账户写在同一个 `FinanceState` 里：`businessAccounts: Record<companyId, number>`。
  不新建第二套账本，也不把银行、就业、股票、贷款改写成多主体模型。
- 余额只能通过 `features/finance` 的公开函数变更：

| 函数 | 语义 |
| --- | --- |
| `openBusinessAccount(state, id, ctx, opening)` | 开户；`opening` 仅用于**世界初始化的明确注资**，会留下来源为「外部投资人」的流水 |
| `transferPersonalSavingsToBusiness` | 个人存款 → 企业账户，真实扣个人资金 |
| `transferBusinessToPersonalSavings` | 企业账户 → 个人存款，只允许 `business-dividend` / `business-liquidation` |
| `receiveBusinessRevenue` | 外部客户 → 企业账户（销售收入） |
| `payBusinessExpense` | 企业支出；余额不足返回 `shortfall`，不抛错、不透支 |

- 企业账户**不得**被当成 `external`：任何入账都必须有真实来源（客户、个人出资、外部投资人开局注资）。
- 资金与流水在同一次 `GameStore` 提交中改变；企业模块禁止直接写 `finance.businessAccounts`。

### 收支口径

- 个人月报 `monthlyTotals` 只统计「一端是个人账户」的流动；企业出资、清算分配属于资本进出，不计入。
- 企业收支 `businessMonthlyTotals` 按 `companyId` 独立统计；出资、分红、清算分配不属于经营收支。
- **经营报表的权威口径是企业状态里的当月累计 `accrual`**，不用被裁剪的最近 2000 条流水反推。
- 未付的成本与工资计入当期费用（应计制），但现金没有减少；两者在界面上分开显示。

### 权益与净资产

```
企业账面权益 = 企业现金 − 企业应付费用（应付工资 + 应付经营费用）
个人净资产 = 现金 + 银行存款 + 未发工资 + 股票市值 + 企业账面权益 + 持有物业估值
             − 生活欠款 − 未偿贷款本息
```

- 持有物业估值只计玩家**产权**持有的住宅与土地（参考估值合计），只计一次；
  永久居住权不属于玩家产权，因此不计入净资产，也不产生房租。
- 房地产买卖不计入个人收支：买入是现金转资产，卖出是实现价差与资产互换。

- 企业权益只计一次，不再额外重复加企业现金。
- 已清算的公司不计入权益；未清偿部分不追索玩家个人资金。
- 产品未来收益、品牌价值、市场估值都不计入。

## 九、研发、代际与产品契约

### 科技水平

```
有效科技水平 = 永久科技积累 + 当前科研高管能力
```

- 永久积累初始 10；只通过「技术积累投入」增长，与单款产品研发预算互不重复计算。
- 高管贡献只取当前任职者；替换或解雇后重新计算。
- 产品立项时锁定基础科技值，后续换高管不追溯。
- 三家 AI 的有效科技固定为 40 / 30 / 15，不随投入增长。

### 研发时长收益

```
t = min(计划天数, 720)
t ≤ 90 :  F(t) = t / 90
90 < t ≤ 720 : x = (t − 90) / 630 ;  F(t) = 1 + 2x − x²
```

`F(90)=1`、`F(720)=2`，90 天后边际收益递减，720 天后不再增长。

### 属性

```
G  = 预算 / (预算 + 参考预算 1,000 元)
原始值_i = 立项科技值 + 40 × G × F(t) × 系数_i        （重点 1.4，其余 0.8）
属性_i   = 100 × (1 − e^(−原始值_i / 100))
单位成本 = 20 元 + 0.4 元 × 平均属性                  （完成时锁定）
```

属性保留内部精度，只在界面显示时取整；不含随机数。

### 发布与代际

- 每家公司同时最多一个研发项目；立项时一次付清预算，取消不退。
- 每个游戏年（360 天）最多发布一款产品；发布资格与研发时长无关。
- 发布时赋予不可变代次（`latestGeneration + 1`），仅研发完成不发布不产生影响。
- 代际系数 = `0.5 ^ (最新代次 − 本品代次)`，在结算时按代次现算，不做累计折扣。
- 旧产品**不自动降价、不自动退市**；玩家可主动停售，停售后不自动恢复。

### 市场

```
Q = Σ 群体权重 × 该群体对（性能, 可靠性, 易用性）的加权分     （0～100）
日销量 = 10 × (Q / 50)² × 营销系数 × 代际系数
营销系数 = 1 + M / (M + 100 元)                              （范围 1～2）
```

- 售价**不影响销量**；没有价格敏感度、没有竞争份额、没有供库存上限、没有消费者钱包耗尽。
- 销售额按游戏时间连续累计，不足一件的余量保存在产品上，累计到整件才成交。
- 改价、改营销、发布、退市前必须先结算到当前时刻，禁止追溯影响过去销量。
- 销售成本按「售价无关、由属性锁定」的单位成本计入；不够现金时记为企业应付，不取消销量。

## 十、时间事件顺序（所有入口一致）

```
a. 个人工资应计、个人贷款利息计提、企业高管工资应计与营销/运营费应计（按分钟）
b. 股票行情节点（跨几个处理几个）
c. 日界：各公司当日销售 → 费用付款 → 危机检查
d. 月界：个人月结（原八步）→ 企业工资付款与企业月报（切换当月累计）
e. 个人贷款到期扣款
f. 研发完成
g. AI 资本决策 → AI 经营决策（同一节点各只执行一次，且必须在该时刻的日结/月结完成之后）
h. 汇总关键事件，决定是否停止本次跳时
```

> 本作的月界与日界是同一刻（月末 24:00）。第 1 个月因为从 08:00 起算只有 42,720 分钟，
> 工资按分钟计，因此首月工资略低于月薪，这是定价口径而非缺陷。

- 同一时刻只处理一次；所有入口共用 `advanceGameTime`。
- 关键事件（玩家研发完成、玩家公司进入资金危机）可在该时刻提前停止跳时，
  并返回实际推进分钟数、剩余分钟数与停止原因。
- 工作被提前停止时只计已完成工时与工资，不记完整班次。
- 自然流逝不提前停止（帧内余量不能被丢弃），事件仍然完整处理。

## 十一、存档契约（v5）

### 切片

v3 起：`population`、`enterprises`、`technology`、`talent`、`businessAi`；`finance` 增加 `businessAccounts`。
v4 起：企业增加费用检查点 `expenseMinute`、`marketingRemainder`/`opexRemainder`，
应付拆分为 `cogsDue`/`marketingDue`/`opexDue`（`supplyDue` 只保留 v3 遗留），
人才任职关系用 `wageNumerator` 取代 `accruedMinutes`。
v5 起：`market` 增加 `candles`（已收盘 K 线，上限 120）与 `candleCurrent`（未收盘）。

### 必须保存

企业身份/归属/状态/应付/当月累计/月报；永久科技、研发项目（预算、立项科技、计划时长、起止时刻）；
产品属性、代次、售价、营销、在售状态、销量余量、累计销量与收入成本；
高管任职与任职分钟；AI 上次决策时刻与产品序号；已结算月份与月报。

### 迁移（v2 → v3）

- `v1 → v2 → v3` 依次执行；v1 先补行情/持仓/贷款，再补经营切片。
- 保留个人资金、贷款、股票、就业、生活欠款、时间与位置。
- 玩家初始没有公司，不获得任何企业资金。
- 三家 AI 从**迁移时刻**开始经营：不追溯销售、工资与研发；首款产品仅有初始状态、累计销量为 0。
- 迁移使用深拷贝，不就地改写传入的存档对象；同一份旧档解析两次得到相同结果，不会重复注资。
- 版本高于当前：拒绝并提示。

### 迁移（v3 → v4）

- 费用检查点从**旧档当前时间**起算，不追溯估算无法恢复的历史预算。
- v3 的 `supplyDue` 混合了成本/营销/运营，无法可靠拆分类：原额保留为「历史经营应付」，
  不凭空推算分类、不重复计入历史费用；补付时按经营费用记账。
- 旧档里已累计但未结算的任职分钟一次性折算成工资（整数分），转入 `payrollDue` 与当月 `accrual.wages`；
  原有 `payrollDue` 是此前未付部分，直接保留，不覆盖、不重复累计；折算余数（不足一分）无法恢复。
- 不重建 AI 公司、不重复注资；同一份旧档重复解析不会再次增加工资或费用（迁移用深拷贝）。
- 不伪造修复旧版月报；v3 及更早的历史报表保持原样。

### 校验新增项（字段关系，不只是类型断言）

- 每个企业必须有同名企业账户；每个企业账户必须有对应企业。
- 每家企业必须有科技切片；任职数据的 `companyId` 必须存在。
- 企业 `lastSettledMinute` 不得晚于当前游戏时间；已清算必须有清算时间。
- 研发项目：`1 ≤ 计划天数 ≤ 3600`，且 `endMinute === startMinute + 天数 × 1440`。
- 产品：未发布不得有代次、不得在售；已发布代次 ≥ 1 且售价 ≥ 1 分；
  销量余量必须在 `[0, 1)`；营销预算不超过上限。
- 人才：候选人必须在名单内，且同一候选人不得被两家同时雇佣。
- 人口：权重合计必须为 1，偏好非负。
- v4：费用检查点不晚于当前时间；营销/运营余量必须小于一天；五类应付均非负；
  工资余量必须小于一个计薪周期。

## 十三、K 线与界面契约（v0.4）

### K 线聚合

- 周期固定 120 游戏分钟（`MARKET.candleMinutes`），起点按 `floor(minute / 120) * 120` 对齐。
- 开盘价取「周期开始时的有效价格」，即本周期第一次更新**之前**的价格；
  最高/最低包含周期内全部有效价格；收盘价是本周期最后一次更新的价格。
- 跨周期时先收盘上一根、再开新的一根；边界时刻的价格只属于新周期，不会重复计入。
- 未收盘 K 线实时更新，界面必须标明它尚未收盘（半透明绘制）。
- 已收盘 K 线上限 `MARKET.candleLimit = 120`，超出丢弃最旧的。
- 只在 `advanceMarket` 内聚合：打开界面、切栏目、点卡片都不会生成 K 线。
- 一次性跳时（休息 / 睡觉 / 推进到下一事件）与分段自然流逝得到完全相同的 K 线与随机状态。

### 存档（v4 → v5）

- 旧档的 `candles = []`、`candleCurrent = null`：历史无法从稀疏价格点还原，明确不追溯。
- 现价、持仓、随机状态、下次更新时间一律不动。
- 校验：周期对齐、价格 ≥ 1 分、`high ≥ max(open, close)`、`low ≤ min(open, close)`、
  已收盘严格递增且不超上限、未收盘不得早于最后一根已收盘。

## 十五、资本契约

### 股权与 CEO

- 持股数量以 `equity.books[*].holdings` 为权威；`securities.holdings[*]` 继续保存成本、已实现盈亏、
  成交笔数与兼容股数。两边股数必须在同一次提交内同步，读档校验不一致即拒绝，不做静默覆盖。
  展示、估值与交易预览通过 `playerHoldingOf` / `playerSharesOf` 读取权威股数；证券终止后估值为 0。
- 一本股权簿对应一只证券；`totalShares = Σ 股东持股 + 库存股`，始终成立。
- 玩家新建公司：初始股份 **100% 归创始玩家**，`sponsorGrantShares = 0`。
  做市商不得在建簿时获得无偿股份；上市后做市库存只能来自真实转让（玩家主动卖出）。
- 三家 AI 公司：历史配置 `founderRatio 0.7 / marketMakerRatio 0.3`，
  以 `sponsorGrantShares` 记录其无偿份额并写明来源；不走玩家公司的初始化路径。
- CEO 与持股解耦：`ceoId ∈ {null, 'player', 'ai:<companyId>', 'inv:<investorId>'}`。
  任职后卖光股份不会让字段非法；职位只由治理流程改变。无 CEO 时由 AI 代管经营。
- 查询三分：
  - `managedCompany(state)` / `managedCompanies(state)`：按 CEO 身份（与持股无关）；
  - `playerCompanies(state)`：按持股（股东权）；
  - `shareholderCompanies(state)`：持股或任职，用于治理入口；
  - 界面当前选择的公司只存在内存（`PersonalUiQuery.capitalCompanyId`），不进存档。

### 融资

- 顺序固定：`submitApplication` → 到期 `processFinancingResponses`（生成报价 + 预留）
  → 接受/拒绝 → 释放或消费预留。
- 接受报价只有一份实现 `acceptFinancingQuote(state, { companyId, quoteId, atMinute })`：
  1. 校验公司与股权簿、报价未过期；
  2. 校验 `quote.effectiveSharesAtQuote / totalSharesAtQuote` 与当前股本一致（否则 `QUOTE_STALE`）；
  3. 校验该报价自己的预留 `investor:<id>::<quoteId>` 足够；
  4. 投资者 → 公司账户（`equity-financing`，不计经营收入）；
  5. 消费该报价的预留，作废同轮其他报价并释放各自的预留；
  6. `issueShares` + `pushRound`（`sharesBefore` 为发行前总股数）；
  7. 上市公司按加权参考调整公开市场价：`round((旧有效股数 × 旧价 + 到账) ÷ 新有效股数)`；
  8. `settleCrisisAfterCapital`：先付应付，应付清零才恢复经营。
- 玩家命令先校验 CEO 权限再调用；AI 用同一函数，按「资金缺口、报价金额、稀释比例」选择
  一份可兑现的报价，缺口过大时全部拒绝。
- 报价有效期结束、公司清算、整轮结束时预留必须释放，不得继续占用投资者资金。

### 资金预留

- key 形如 `investor:<investorId>::<quoteId>`；`reservedOf` 按主体汇总，
  `reservedFor(owner, id, ref)` 取单张单据。
- `reserveFunds` 用「可用余额 = 余额 − 已预留」校验。
- **普通划转**（`transferFunds`）：从 `investor` / `market` 主体扣款时，支出上限同样是
  「余额 − 该主体全部预留」，不得侵占其他有效承诺；个人与企业账户保持原有支付语义。
- **受预留支持的划转**（`transferReservedFunds`）：必须指定 `reservationRef`，
  校验该单据预留足额、真实余额足额，只消费该单据，划款与流水在同一次提交内完成。
- **释放**（`releaseFunds(..., ref)`）：只释放该单据；单据不存在或不足时不做任何补扣。
  主体整体释放必须显式调用 `releaseAllFor`。没有「跳过预留检查」的通用开关。

### 交易与回购

- `previewTrade(state, id, side, shares)`：
  - 买入：`股数 × 含冲击成交价 ≤ 银行存款`，用二分在单调区间内求解，再线性修正取整误差；
  - 卖出：同样受「做市商现金 ≥ 成交额」约束；
  - 另受**做市在售库存**（`stock.forSaleShares`）、玩家持股、`maxOrderShares` 与技术金额范围约束。
- `executeTrade` 重新计算预览：数量变了抛 `QUANTITY_CHANGED`；
  `expectedPriceCents`（界面上确认过的均价）变了抛 `PREVIEW_STALE`。
- `previewBuyback` / `executeBuyback`：公司现金为实际可用现金（不额外扣应付作储备），
  只受库存、现金、单笔上限约束；数量不符时明确拒绝，不缩量；总发行量不变，
  价格影响走 `adjustPrice`（同一份行情与 K 线）。

### 清算与证券终止

- `liquidateCompany`：结清销售/费用检查点 → 付清应付 → 按有效持股分配剩余现金
  → 证券 `terminatedAtMinute` → 持仓结算最终投资结果 → 取消未完成资本事项
  → CEO 置空、未决提案作废、人才释放、公司关闭。
- 终止后 `securityValueOf = 0`，不能交易、不再生成行情；股数、成本与成交记录保留。
- 清算回收款（个人）与「回收款 − 剩余成本」只形成一次已实现盈亏，不重复计入净资产。

### 治理

- 提案含 `origin`（player / shareholder）、`deadlineMinute`、`playerVote`。
- 玩家提案默认赞成并立即结算；外部提案有 `GOVERNANCE_RULES.voteWindowDays` 个游戏日的窗口，
  玩家未投票按弃权，**不会**自动把其股份算成赞成。
- 通过条件 `yes × 2 > 有效股份`；库存股不投票；恰好 50% 不通过。
- 首轮 `maxManagedCompanies = 1`：任命玩家为第二家公司 CEO 必须被拒绝（票数通过也不生效）。

### 存档（v6 → v7）

- 新增：`ShareBook.sponsorGrantShares`、`SecurityMeta/Holding.terminatedAtMinute`、
  `FinancingQuote.totalSharesAtQuote/effectiveSharesAtQuote`、
  `Proposal.origin/deadlineMinute/playerVote`、`GovernanceState.lastExternalProposalMinute`。
- 预留键规范化：旧 `${owner}:${id}` → `${owner}:${id}::legacy`。
- 无法确认基数快照的在途报价：作废并释放预留（不静默补齐）。
- 玩家公司的无偿配股：只收回「初始配比 − 已回购 − 玩家买回」的可识别部分，
  收回的股份同步进玩家证券持仓且不改成本；成交记录被截断时保留现状并写明数据缺口。

### 报价 ID、预留释放与卖出确认（存档 v8 起）

- **宣传强度不是货币**：`PromotionRecord.strength` 是公式算出的小数，
  校验只要求「有限、非负、≤ `PROMOTION_RULES.maxBoostPct`」，失败记录必须为 0；
  金额与时间字段仍按整数校验，不因这一项放宽。
- **提案检查挂在真实日界上**：游戏从 08:00 起算，日界并不落在「累计分钟整除 1440」，
  因此用 `dateAtMinute(...).minuteOfDay === 0` 判断日界、用
  `monthIndex × daysPerMonth + (day − 1)` 作日序号；同一个日界只检查一次，
  月界时排在该次月结**之后**（提案判断要用刚固化的报表与应付）。
  外部提案的截止时刻同样落在日界上，由同一检查点结算。
- **CEO 罢免资格**：`remove-ceo` 只要求目标确实是现任 CEO 且身份合法，不要求其持股；
  候选人资格（`appoint-ceo` 需为股东）与提案人资格（必须是该公司股东）分开校验。
- **报价 id 全局化**：`quote-<申请id>-<投资者>-<股数>`，申请 id 含自增序号，
  因此不同公司、不同轮次的同金额同股数报价不会共用预留键；生成后写入存档，读档不重算。
- **`releaseFunds` 只释放指定单据**：ref 不存在或余额不足时不做任何补扣；
  重复释放无副作用；整体释放必须显式用 `releaseAllFor`。
- **回购是「本次预览 → 明确确认 → 执行」**：预览按玩家输入的股数计算请求量、
  可成交量、含冲击均价、总额、价格影响与不可执行原因；
  确认框展示同一份数字，命令接收 `(companyId, shares, expectedPriceCents)` 并重新校验
  权限、公司状态、现金、库存与价格；数量或价格变化即拒绝，不缩量、不换价。
  参考上限（`maxOrderShares` 下的可回购量）只是提示，不代替本次预览。
- **预算求解**（`maxSharesWithinBudget(base, budget, side, limit)`）：在
  `1 ≤ n ≤ limit` 内求 `n × executionPrice(base, n, side) ≤ budget` 的**最大整数股数**，
  `limit` 由调用方传入（请求量、真实持股/做市库存、单笔上限取小）。
  - 买入：成交价单调不减 ⇒ 总额单调递增，上界 `预算 ÷ 原价` 可证明，二分即精确解。
  - 卖出：成交价单调不增，但取整会让总额在档位边界处回落，**不能对股数直接二分**。
    改为按「成交价档位」求解：同一档内价格是常数、总额严格递增，档内最优解是
    `min(档末, floor(预算 ÷ 档价))`；「档起点 × 档价」沿股数单调递增（相邻档的增量约
    `档价 × 档宽`，大于取整带来的 ±n/2 偏差），因此对股数二分定位最后一个付得起的档，
    再在该档内取精确解。整个过程只调用 `executionPrice`，不复制冲击公式。
  - 求解结果参与 `min` 后再定价一次即成交额，因此卖出总额必然不超过做市商现金、买入必然不超过存款。

### 存档（v7 → v8）

- 报价 id 撞车（同一投资者 + 同一股数出现在不同公司/轮次）：报价明确作废并释放其承诺，
  不猜测归属；唯一 id 的报价原样保留。
- v6→v7 留下的 `legacy` 预留不再对应任何有效承诺：全部释放（只删预留，不动余额、不重新注资）。
- 已保存为 v7 但缺少股权簿的旧玩家公司：走 `ensurePlayerCompanyBook` 补建（幂等），
  补建的簿子 `sponsorGrantShares = 0`，不会被「无偿配股修复」误处理。
- 校验新增：报价 id 全局唯一且不含 `::`；`quoted` 申请的每份报价必须持有足额预留；
  存档中不允许残留 `legacy` 预留单据。

## 十六、产品—股价联动、在售股份与卖出确认

### 两个属性口径

| 口径 | 公式 | 用途 | 位置 |
| --- | --- | --- | --- |
| Q（加权品质） | 按人口偏好加权 | 市场销量，本轮**不改** | `features/market` |
| A（等权平均） | （performance + reliability + usability）÷ 3 | 首次发布对股价的一次性反应 | `technology.averageAttributeOf` |

A 使用原始精度判定，只在界面格式化；两者不得互相替代。

### 首次发布的一次性反应

`app/securities-settlement.applyProductReleaseImpact(state, company, product, atMinute)`

```
t = clamp((P − priceBaseYuan) ÷ priceSpanYuan, 0, 1)   // P = 发布前股价（元）
U = upperBase + upperSpan × t        L = U × lowerRatio
delta = +perPointPct × (A − U)  当 A > U   （上限 +maxImpactPct）
delta = −perPointPct × (L − A)  当 A < L   （下限 −maxImpactPct）
delta = 0                        当 L ≤ A ≤ U
```

- 玩家（`app/business.releaseProduct`）与 AI（`app/business-settlement` 的 `release-product`）
  调用同一个入口，**与发布在同一次 `GameStore` 提交内完成**。
- 幂等：`product.releaseImpactPct` 为 `null` 才计算；成功后写入数值（含 0）。
  重复点击、界面刷新、读档、日结都不会二次施加。
- 未上市 / 已终止 / 无行情：写入 0，不创建证券、不补发历史奖励。
- 价格调整走 `stock.adjustPrice`，进入同一份行情与 K 线。

### 销量因子（有界，作用于锚点）

`salesPerformanceFactorOf(state, company)`：

```
avg  = 最新发布产品最近 salesWindowDays 个完整游戏日的日均实际日销
s    = clamp(avg ÷ PRODUCT_MARKET.baseDailyUnits − 1, -1, 1)
因子 = 1 + salesWeight × s          // 没有完整日记录时返回 1
```

- 只对**上市公司**生效，直接乘进 `fairPriceOf` 的锚点，**不做逐日连乘**，因此不会复利叠加。
- 日销量只在日界由 `business-settlement.recordDailySalesOfLatestProduct` 记录：
  取最新产品 `totalUnits` 的增量，归到「刚结束的那一天」（`boundaryMinute − 1` 的日序号），
  同一天重复调用取较大值，最多保留 `maxDailyRecords` 条。
- 停售 / 暂停 / 危机期间没有销量，窗口自然衰减到 0（因子 0.9）；换新产品后自动观察新产品。

### 在售股份

`stock.forSaleShares(market, deskShares) = min(deskShares, floor(deskShares × forSaleRatio))`

- 唯一口径：`previewTrade`（买入上限与「最多可买」）、`previewBuyback` / AI 回购、
  公司详情饼图全部调用它。
- `forSaleRatio` 首轮 80%，范围 `[0.6, 1]`，每个行情节点随涨跌微调 `maxStepPerTick`（0.5 个百分点）；
  平盘不动。调整不转移股份、不创造资金、不增发、不自动卖出任何持仓。
- 做市库存为 0 或未在售时为 0：买入被明确拒绝并说明原因（不是缺陷）。

### 卖出确认

- 界面只提交 `(securityId, 输入股数, 预览均价)`；「填入全部持仓」只填数字，不执行交易。
- `Game.confirmSell` 先读一次只读视图，确认框显示名称、股数、均价、金额、价格影响与**剩余持仓**，
  玩家确认后才提交；确认框阻塞，期间不会替换玩家看到的数字。
- 命令与结算层继续复核：`executableShares !== shares` → `QUANTITY_LIMIT`；
  与确认均价不符 → `PREVIEW_STALE`；不缩量、不换价。
- 预览在算出 `amountCents` 后显式比较付款方余额（买入=银行存款，卖出=做市现金），
  超出即返回不可成交；`assertMoneyRange` 只校验数值范围，不代替余额比较。

### 行情调度、日销量与详情刷新（存档 v10 起）

#### 行情调度 ≠ 价格历史

- `nextTickMinute` 只表示**下一次定时行情**；`history` 还会收到交易、回购、分红、增发、
  产品发布等即时价格事件（`adjustPrice`）。二者是两条时间序列，**不能**用
  「最后一条历史时间 + `MARKET.tickMinutes`」推断调度时刻。
- 校验规则（`storage.validateSecurities`，新增参数 `nowMinute`）：
  - 时间/价格字段、历史严格递增、**历史不得晚于当前游戏时间**、最后价格等于现价、随机状态与 K 线不变；
  - 仍在运行的证券：`nowMinute < nextTickMinute ≤ nowMinute + MARKET.tickMinutes`；
  - 已终止证券或已清算发行公司：不要求 `nextTickMinute` 追赶当前时间（行情已停止推进）。
- `adjustPrice` 不修改 `nextTickMinute`：即时价格事件不重排定时行情。

#### 日销量只取完整游戏日

`Product.dailyObservationStartMinute` 记录观察起点（游戏分钟）。

- 初始化：`completeProject` 待发布产品为 0；`addSeedProduct` 为开局时刻；
  `releaseProduct` **正式发布时**重置为当前分钟并把 `daySnapshotUnits` 对齐 `totalUnits`。
- 日界（`business-settlement.recordDailySalesOfLatestProduct`）：
  1. 先由统一销售结算把销售结清到日界；
  2. 刚结束的完整日区间是 `[boundaryMinute − minutesPerDay, boundaryMinute)`；
  3. `dailyObservationStartMinute ≤ boundaryMinute − minutesPerDay` 才算**覆盖完整日**，
     此时把 `totalUnits` 增量写入 `dailySales`（日序号 = `daySerialAtMinute(boundaryMinute − 1)`）；
  4. 不足一天时**只**更新 `daySnapshotUnits` 与观察起点，不写样本；
  5. 无论是否写样本，观察起点都推进到该日界 → 同一日界被日界/月界各处理一次时不会重复记录。
- 估值：没有完整日样本时因子为 1；有样本后沿用最多三日窗口与有界因子（±10%）。
  暂停/停售后的完整日零销量仍是有效样本。

## 十三、人口、政治与政府契约（v11 引入，v12/v13 修正）

本节描述「城市政府、选举与动态人口」这一轮新增的公共规则。数值参数集中在
`content/population.ts` 与 `content/government.ts`，业务代码不得内联。

### 13.1 人口（唯一权威）

- 初始：10 万人，低 50% / 中 35% / 高 15%（`POPULATION_RULES.initialRatios`）。
- 自然增长：每年 2%，`N(t) = N0 × 1.02^(t/360)`，t 为游戏日（每月 30 天、每天 1440 分钟）。
  - 只随游戏时间增长：暂停、关闭、后台暂停都不补算离线增长；
  - 用固定锚点的指数比实现，**一次推进与分段推进结果一致**；
  - 新增人口按当时阶层结构分配（三层同乘同一比例）；
  - 阶层流动**不改变总人口**；显示整数用最大余数法，保证各层之和等于显示总人口。
- 月度基础流动率（来源人数 × 比例）：低→中 0.0028、中→低 0.0040、中→高 0.0012、高→中 0.0028。
  四条路径从同一份结算前快照计算，同一居民不会在同月连续升降两级，没有高→低或低→高直接通道。
- 经营修正（`j/i/p` 为企业等权的原始有界值；**0.30 权重在人口模块内乘一次**）：

```
bLM = max(0, 0.0028 + 0.0012J + 0.0006I − 0.0012P)
bML = max(0, 0.0040 − 0.0015J + 0.0030P)
bMH = max(0, 0.0012 + 0.0004J + 0.0008I − 0.0006P)
bHM = max(0, 0.0028 − 0.0008I + 0.0020P)
```

  - `J`（就业薪酬机会，[-1,1]）由任职覆盖与实际工资水平决定，并扣除工资拖欠率；
  - `I`（产业发展，[-1,1]）由实际研发投入与高能力岗位决定；
  - `P`（经营压力，[0,1]）由工资拖欠、其他经营拖欠、非正常经营时长与当月清算决定；
  - 当前只有少数可模拟企业，因此这些指标代表「**可模拟企业样本**」，界面必须如此标注，
    不得显示成全市实际就业率。

### 13.2 证券财富效应

- 投资参与比例（群体统计暴露，不创建居民账户）：低 0.10 / 中 0.35 / 高 0.75。
- 综合市场月回报 `R` = 当月样本证券**等权调整后**回报的算术平均；
  涨跌覆盖比例 `Bdown / Bup` 把平盘样本计入分母。
- 参考财富口径（唯一）：`参考基准 = 月初价格 × Π(机械事件后价格 ÷ 机械事件前价格)`，
  `累计现金 = Σ 每笔分红 × 该笔分红之后所有机械事件的价格比例`（即换算到当前价格尺度），
  `样本回报 = (期末价值 + 累计现金) ÷ 参考基准 − 1`。
  增发摊薄只累乘参考因子（`referenceFactor`），机械事件当刻回报为 0；
  之后的真实涨跌完整保留；分红现金在清算时也不被抹掉；多次机械事件只继续累乘。
  **累计现金必须与参考基准同尺度**：机械事件时现金随参考因子同比例换算，
  否则「先分红、后增发」会把同一笔现金重复放大（100 → 分红 20 后 80 → 机械 40，
  错误 +20%，正确 0%）。禁止用绝对价差相加，也禁止夹住/清零回报来通过参考案例。
- 冲击强度：

```
D = Bdown × clamp((−R − 0.05) / 0.35, 0, 1)
U = Bup  × clamp(( R − 0.05) / 0.35, 0, 1)
```

- 最终月流动率：

```
rLM = bLM × (1 − 0.8D) + 0.10 × 0.15 × U
rML = bML                 + 0.35 × 0.35 × D
rMH = bMH × (1 − 0.8D) + 0.35 × 0.12 × U
rHM = bHM                 + 0.75 × 0.50 × D
```

  最大额外下跌影响：中→低 12.25%、高→中 37.50%；最大额外上涨影响：低→中 1.50%、中→高 4.20%。
  经营贡献的 30% 上限**不**用于削弱股票冲击。
- 依据当月回报，不按距离历史最高点重复处罚：低价横盘不会持续产生新的股灾损失。
- `R` 与各样本回报都是**原始收益率**，校验只拒绝 NaN / Infinity，不限制合法涨幅上界；
  经营指标 `j/i/p` 才是经过 0.30 权重的有界值，两者校验口径不同。
- 玩家个人交易只影响个人账户；不因玩家个人盈亏额外改变全城人口。
- 样本规则：月初固定样本（含独立标的与正常上市企业证券）；月中上市下月加入；
  月中终止仍计入本月；没有有效样本时股市影响为中性。

### 13.3 政治人口与选举

> **v16 已替换本节的政治群体口径**：旧的 4 个群体（创新发展 22% / 就业稳定 30% /
> 公共服务 28% / 综合务实 20%）与 `[-1,1]` 满意度不再存在，现行口径是 3 收入 × 4 利益 =
> 12 个交叉群体、满意度 0～100，见第二十二节。本节的支持率公式、资格比例、票数守恒、
> 平票抽签与竞选/赞助规则继续有效；12 群体的 `turnout` 与 `match` 来自
> `content/politics.ts`，其中生活成本群体是新增配置，不是旧「综合务实」改名。

- 12 个交叉群体的投票率：科技与创新 0.58 / 商业与就业 0.68 / 住房与基础设施 0.62 /
  生活成本与消费 0.64（四个利益方向共用；生活成本匹配 A=0、B=0.6、C=0.4）。
- 支持率：`Ugc = Bgc + Pgc + Egc + Igc + Agc`，`sgc = softmax(Ugc / T)`，`T = 0.75`（数值稳定实现）。
  每个群体对全部候选人的支持率之和为 1；没有每日随机扰动。
  - `Pgc = 0.90 × 政策匹配系数`；
  - `Egc = 0.45 × 群体满意度 × max(0.25, |政策匹配|)`，满意度只引用有来源的经济摘要；
  - `Igc` 只给现任候选人：`0.15 + 0.25 × clamp(0.8J + 0.5I − P, −1, 1)`；过渡负责人没有这项加分；
  - `Agc = 宣传能力 × Amax × X/(K+X)`，`X` 是本届**已使用**资源（不是收到的赞助额）。
- 票数：合格人数 = 总人口 × 0.72；
  群体参与人数 = 总人口 × 0.72 × 群体比例 × 群体投票率；
  候选人票数 = Σ 群体参与人数 × 该群体支持率。整数化用最大余数法，票数之和恒等于参与人数。
  - `groupPeople` 已经是「总人口 × 群体比例」，所以计算参与人数时**只再乘**资格比例与投票率，
    不能再乘一次群体比例；参与人数不得超过合格人数。
  - 该口径只有一份实现（`features/elections.estimateTurnout`）：开票、界面「预计参与」、
    候选人「预计有效票」与投票率共用；界面不得再写一套近似公式。
  - 界面上「全人口加权支持率」= Σ 群体比例 × 群体内支持率（不乘投票率，不是预计有效票占比）；
    「预计有效票」= 参与人数口径 × 群体内支持率整数化结果。两者措辞不得混用。
- 相对多数制；**仅实际整数票平票**时用独立持久化的 PRNG 抽签（不消费行情随机数，读档不重抽）。
- 零有效票：过渡负责人留任，30 天后重选；投票率偏低但有有效票时结果有效，界面提示。
- 开局是中性过渡负责人：不享有三位候选人的产业政策，也不获得现任竞选加分。

### 13.4 竞选与赞助

- 任期 360 游戏日，竞选期 30 游戏日；新游戏在**第 30 天 08:00** 首次投票
  （开局为第 1 天 08:00、`totalMinute = 0`，因此首次投票相对开局是
  `(30 − 1) × 1440 = 41760` 分钟，不能再额外加一次 08:00 偏移）。
  实际竞选时长 29 个完整游戏日；后续投票时刻 = 上一届投票时刻 + 360 天，竞选在投票前 30 天开启。
  旧档迁移的「迁移时刻 + 30 天」规则保持独立，不套用新游戏公式；不追溯重演已完成的选举。
- 资源：每届基础 900,000（三位候选人相同；新游戏、旧档迁移、后续竞选与零票重选共用同一初始化），
  每日使用上限 300,000（按实际经过分钟折算，首个不满一天按实际时长结算）；
  1 分赞助 = 1 单位资源；`K = 3,000,000`，`Amax = 1`。未使用的资源届末失效，不退款、不结转。
  - 赞助到账前必须先按**旧资源**结清到当前时刻，新资源只能用于到账之后的区间；
    无资源期间不积攒可结转的整日额度；资源不足一天时保留的是分钟余量而不是历史额度。
  - 读档与重复开启竞选不得再次发放基础资源。
- 赞助规则：**仅从个人存款扣款**（不动用现金、企业资金或贷款），金额为正整数分；
  余额不足整体失败（不接受部分扣款）；`atMinute >= deadline` 一律拒绝；
  扣款、流水、单据与资源在**同一次提交**内完成；同一 `requestId` 重试不会再次扣款；
  赞助计入个人支出，不计入企业经营费用；确认框中的金额、候选人与确认范围不得在提交时被替换。

  旧档从迁移时刻起安排一届完整竞选（30 天后投票），不补演历史选举；

- v11 → v12（本轮的修复性真实迁移）：
  - 市场观察样本的 `mechanicalOffset`（绝对价差）改为 `referenceFactor`（乘法参考因子）。
    旧格式无法无损还原历史价格比例：若剩余观察月内曾发生机械调整，将该不完整月标记为中性

  - 首届竞选基础资源错误为 0：只对 `base === 0` 的候选人补到 900,000，并把资源锚点移到迁移时刻，

  - 迁移链 v1 → … → v12 完整保留；纯校验调整不占版本号。
- v12 → v13（分红现金计量尺度修复，仍是持久数据语义变化）：
  - 累计分红现金改为随机械价差换算到当前价格尺度；旧档无法判断分红与机械事件的先后顺序，

  - 历史已结算的市场摘要属于既成事实，不重算、不伪造。

    不与经过 0.30 权重的有界经营指标共用 [-1,1] 范围；合法大涨（如 +120%）可正常读档。
- 读档不重复增长、扣款、用资源、抽签、流动或生效政策；校验只读不修；
  导入失败不替换当前有效游戏；不改用户自定义名称与历史流水文字。
- 校验只读不修：当前版本缺失/损坏的必要字段（如 `settledTerms`、`tieRng`、

  不能把「损坏的当前版本字段」当成旧档兼容自动补默认值。

### 13.7 界面契约（政府面板）

## 十四、人物生存、物品栏与便利店契约（存档 v14）

### 14.1 生存值与效率

- 饱食度、水分相互独立，范围 0～100，新游戏均为 100。
- 内部单位：每点 2880 单位，满值 288000；每游戏分钟消耗 100 单位（满值到 0 恰好 48 游戏小时）。
  状态只存内部单位整数，**不得**用浮点反复累减或近似 2.083。
- 只在 `app/timeAdvance.advanceGameTime` 的区间内消耗一次；暂停、后台、关闭游戏不消耗、不补算离线。
- 效率与移动倍率由当前状态**推导**，不另存权威副本：
  - `E = max(0, 1 − 0.5×[饱食度=0] − 0.5×[水分=0])`
  - `M = max(0, 1 − 0.15×[饱食度=0] − 0.15×[水分=0])`
  - 结果：满/单项归零/双项归零分别为 `E=100/50/50/0%`，`M=100/85/85/70%`。
- 低于 20 只提示，不产生惩罚；没有死亡、扣血或游戏结束。0% 效率不产生工资、不扣钱、仍可移动/购买/使用。

### 14.2 物品与背包

- 物品目录只含稳定 `itemId`、名称、说明、类别、可用性与恢复效果；**价格不在物品上**。
- 首版物品：面包（饱食度 +15，5 元）、便当（+45，15 元）、矿泉水（水分 +25，3 元）、
  运动饮料（+40，8 元）。金额内部为整数分。
- 背包：`itemId → 正整数数量`，同类堆叠、不限制格数、数量为 0 删除条目；禁止负数/NaN/Infinity/不安全整数。
- 恢复立即生效、clamp 到 100；部分溢出允许并显示实际恢复与浪费；满状态使用会 100% 浪费时拒绝，不消耗物品。
- 不做装备、耐久、重量、体积、合成、烹饪、保质期、逐件实体。

### 14.3 商店与购买

- 便利店 `shopId = convenience-store`，首版 24 小时营业、无库存/补货模拟。
- 购买仅使用个人现金；现金不足整体拒绝，不自动动用存款/企业资金。玩家可先用银行取现。
- 购买要求当前真实商店交互上下文（通过便利店建筑 F 进入面板时建立，关闭/切换面板/读档即失效），
  不能仅凭 UI 存在远程购物。
- 金额 = 单价 × 正整数数量，必须通过金额范围检查；扣现金、财务流水（类别 `supplies`）、
  增加物品与请求去重记录在**同一次**提交内完成。
- 使用可从背包直接执行，无需回到便利店；扣除一件并恢复生存，同一次提交；不扣钱、不产生零金额流水、
  不推进游戏分钟。
- 请求协议（购买与使用共用同一序列，不允许各用一条会撞号的序列）：
  - `InventoryState` 持久化 `operationEpoch`（本存档命名空间，新游戏/旧档迁移生成一次，读档不重生成）
    与 `nextOperationSeq`（从 1 开始，只有成功操作才 +1）；
  - requestId 固定格式 `supplies:<operationEpoch>:<sequence>`，sequence 为无前导零的正安全整数；
    完整格式解析，不截取末段信任；旧 random UUID 请求不被升级、不被猜测归属。
  - sequence < nextOperationSeq：有收据则核对 kind/shopId/itemId/quantity 后判为 REPLAYED
    （不扣款/不扣物品/不恢复/不推进序号）；没有收据则 REQUEST_EXPIRED（历史已被裁剪，绝不再次执行）。
  - sequence > nextOperationSeq：REQUEST_OUT_OF_ORDER；sequence = next：才进入业务校验与写入，
    写入成功后落收据并 next+1；任一步失败整份草稿回滚、序号不变。
  - sequence 到安全整数边界时 REQUEST_SEQUENCE_EXHAUSTED，不回绕 1。
  - 收据最多 64 条，含 `protocolVersion=1`、sequence、requestId、kind、shopId（购买为实际店 id，
    使用为 null）、itemId、quantity、atMinute；裁剪不影响高水位序号。
  - 视图只暴露 `requestCursor`（epoch/next/requestId），读取不消耗序号；UI 提交前固定本次内容与
    requestId，同一次重试复用；过期/乱序/非法时清理 pending 并刷新，要求重新操作。

### 14.4 工作衔接与工资精度

- 行政岗位 60 元/小时保留；便利店岗位 45 元/小时；班次 4 小时、最短 1 小时、每日最多 8 小时、9:00～18:00。
- 一次只能在一个岗位在职；切换岗位只改岗位，保留已赚工资、今日实际工时、班次数与工资余数。
- 有效计薪分钟 = 实际出勤分钟 × E，E 取每个时间区间**开始**的生存状态；先计薪、再消耗生存。
- 唯一计薪实现：分子 = 时薪(分) × 分钟 × 效率百分比(0～100) + 余数，按 6000 折成分；
  不先把有效分钟或 50% 时薪取整。效率 100% 时结果与旧版一致。
- 每日上限按**实际出勤分钟**执行（`workedMinutesByDay`），0% 效率出勤同样占用上限，不能绕过而额外出勤。
- 归零点之后的后续区间才按降低后的效率计薪，不能用班次结束状态追溯整个班次。
- `AdvanceResult` 返回本次实际出勤 `workedMinutes` 与折算有效计薪 `effectiveWorkMinutes`
  （每个工作区间用同一份区间开始 E 同时计薪与统计）；两者都是本次推进的统计，不进存档。
  工作提示的平均效率 = effectiveWorkMinutes / workedMinutes；没有出勤统计时明确显示
  “无有效出勤统计”，不得把起始效率无标签地当成整班效率。
- 月结仍按 `accruedByMonth` 发放，不清空未结清的工资精度余数；已赚工资不因生存状态改变而追溯扣减。

## 二十一、城市经济统计与连续指数（v16）

### 21.1 游戏 GDP 口径

```
G0   = 开局各本地在售产品预计日产出之和 × 360    （`CITY_ECONOMY_RULES.baseGdpDays`）
P(t) = 观察开始后累计经营产出（不按月/年清零）
S(t) = round(G0 × 0.30 × (I(t)/100 − 1))
G(t) = G0 + P(t) + S(t)
```

- 金额单位为分，`G0` 只生成一次并写入 `cityStatistics.base`（含 `ruleVersion`、`generatedAtMinute`、
  `source ∈ {new-game, migration}` 与来源说明）；读档与迁移都不得重算。
- 新游戏的 `G0` 用既有 `estimateSales` 从**初始在售产品**估算；旧档迁移用**本版本标准开局条件**
  （`AI_COMPANIES` 首款在售产品 + 标准人口偏好）生成背景估算，不用玩家当前高价产品反推。
- `P(t)` 只来自 `settleCompanySales` 的成功结算：实际售出数量 × 当时实际成交单价。
  登记用企业操作序号单调高水位（`output.cursors[*].outputSeq`）防重复；序号可有间隔，
  不要求连续。清算前的产出保留。不得从被裁剪流水、最新价 × 历史销量、月报求和或市值差额反推。
- `P(t)` 有两个查询口径，必须区分：
  - **实时口径**（界面、政府面板总数 / 组成公式 / 累计产出 / 建设门槛差额）：
    `P实时 = 已结算累计 + 当前可结算但尚未入账的产出`，`G实时 = G0 + P实时 + S`；
    待结算来自唯一的只读投影 `pendingOutputCentsOf`（内部就是 `computeSalesPlan`），
    查询不推进游标、不改余量、不写财务、不写统计；**不得**把待结算写入持久累计。
  - **已结算口径**：`settledGdpCentsOf(state)` 使用持久累计，只在「销售已全部结清」的场景使用
    （选举前按旧任期属性结清全部销售 → 本任期唯一一次建设判断）。此时待结算为 0，两者相等；
    实时界面不得调用它。
  - 同一时刻、无新时间与价格变化时，仅把待结算转为正式结算：`settled += pending`、
    `pending → 0`，实时累计与实时 GDP **不跳变**；`monthOutputCents` 只在正式登记时增长。
- 股票只通过 `S(t)` 进入 GDP：股票成交额、融资、增发到账、贷款、个人资产变化、
  旧资产转手都不计入经营产出；没有真实业务数据的服务业与纯模型价值也不计入。
- GDP 不是现金：不创建任何 GDP 财务账户；界面必须显示「已结算 / 待结算」的组成。
- 金额校验：G0、已结算、待结算、实时累计与实时 GDP 都必须是有限非负安全整数，
  异常抛错而不是静默夹值。

### 21.2 销售纯投影（唯一实现）

`app/city-statistics.computeSalesPlan(state, companyId, nowMinute)`：

- 输入只读产品、销售余量、结算游标、时间区间与既有市场参数；
- 输出每条产品的可结算件数、收入、成本与结算后的余量（含 sold=0 时余量已增长的情况）；
- **纯只读**：不推进游标、不改余量、不写财务、不补建科技切片；
- 正式 `settleCompanySales` 与实时统计预览共用这一份计算，不得另写近似销量公式。

`monthKey` 归属由调用方按企业 `accrual.monthKey` 传入：月界当刻结清的旧区间属于旧月，
月界之后的 AI 决策结算属于新月份 accrual，不得用 `nowMinute` 推算（会串月）。

### 21.3 连续全市场指数

```
指数 = 窗口起始指数 × 有效样本财富倍数的等权平均
样本财富倍数 = (当前价格或终止回收价 + 已分配每股现金) ÷ (样本基准价 × 累计机械参考因子)
```

- 起点 100；旧档从接入时刻 100 开始，不反推缺失历史。
- 窗口内样本固定：月中新上市的下个月进入样本；月中终止的样本保留到本窗口结束。
- 月底先固化当前指数，再作为下个月窗口起始指数；链结幂等（同一 `monthKey` 重复调用不改状态）。
- 机械调价（增发等）：`referenceFactor` 与累计 `cashPerShare` 同时乘 `priceAfter / priceBefore`。
- 分红：只累计真实每股现金分配；除息已体现在现价里，不再额外补偿。
- 清算：用真实每股回收价值，不通过立刻移除亏损样本抹掉跌幅。
- 无有效样本时保持已有指数并标注样本不足，绝不静默回到 100；指数与因子必须有限、非负。
- 与 `population.marketWindow` 是**两套独立窗口**：数学口径同源，但不共用可变状态、
  不改变人口观察的完整月规则；GDP 的首个不完整窗口仍可实时工作（摘要 `valid=false`）。

### 21.4 月界固化与统计快照

`app/city-statistics.snapshotCityMonth` 在企业月结之后、人口月结与建设判断之前执行：
先固化指数窗口，再落一条 `CityMonthSnapshot`（基础 GDP、累计与本月产出、股市调整、GDP、
指数、样本数、产业拆分），最多保留 24 条。这些快照只用于展示趋势，**不限制建设**。

行业拆分只使用真实经营产出（本轮唯一纳入的是科技产业），股市调整单独展示，
不会作为负产业面积进入饼图。

## 二十二、12 交叉政治群体、满意度与提前选举（v16）

### 22.1 群体与人数

- 3 收入阶层（low / mid / high）× 4 利益归属（innovation / employment / housing / cost）
  = 12 个互不重复群体，稳定 ID 形如 `low:innovation`。
- 条件权重（同一阶层四个权重合计 1）：
  低收入 15/35/25/25%、中收入 25/30/25/20%、高收入 35/20/25/20%。
- `N(收入,利益) = population.classes[收入] × 该收入内部权重`；政治切片**只存满意度与监测计数**，
  不保存第二份权威总人口或另一份阶层人数。
- 收入边际（3）与利益边际（4）是展示与监测视角，不能再加到总人口上。
  本轮不模拟逐人政治身份，阶层变化后由新阶层人数与条件权重重新派生。

### 22.2 满意度

```
T   = clamp(50 + 10M + 15E − 25P − 10C + 10D − 12×(H − 0.5), 0, 100)
S新 = S旧 + clamp(0.20 × (T − S旧), −4, 4)        （clamp 到 0～100）
```

- `H`（住房压力，0～1，0.5 中性）来自住房模型固化的**当月**指标，按群体所属收入阶层取值；
  当月没有住房样本时按中性处理。它不读取玩家个人收支，也不是「全城生活成本」C。

- `M`：当前执政方向与群体利益的政策匹配（`content/politics` 的 `match`，[-1,1]）；
  过渡负责人 M=0。`E = clamp(0.6×rawJ + 0.4×rawI, −1, 1)`；`P = clamp(rawP, 0, 1)`。
- `C`（全城生活成本恶化）：当前版本**没有真实的全城物价/居民生活成本数据源**，
  应用层统一传 `{ costPressure: 0, hasCostSample: false }`，按中性处理。
  禁止从玩家个人欠租、个人贷款、个人现金或个人购物支出推导全城成本压力
  （玩家投资/赞助后交不起租，不是城市物价上涨，不能降低全体市民满意度）。
  以后若要实现，必须是独立设计、有真实数据来源的分层物价指标，不能改造既有满意度输入冒充。
- `D`（建设履约）必须绑定**当前真实任期**：`deliveryOf(state, nowMinute, currentTermId)`，
  `currentTermId` 取 `government.currentHolder.termId` / `activeTermOf(...).id`（不得用 `elections.termSeq`）。
  只统计 `sourceTermId === currentTermId` 且 `completeAtMinute <= nowMinute` 的到期承诺：
  已完成数 / 到期承诺数；本任期没有到期承诺（含尚未到计划完成时刻的在建项目）→ 中性，
  不扣分。前任项目（含前任批准、后任期间才完成）不计入本任期履约。
  历史城区、项目与完成记录全部保留，换届不删除城区。
- **尺度还原**：人口月结记录的 `business.j/i/p` 已乘 0.30，满意度使用前必须除以
  `SATISFACTION_RULES.restoredBy`，不得重复乘权重。
- 缺失数据时对应项中性（C/D 无样本记 0），不伪造住房供给改善；未达门槛没有承诺项目不算失信；
  尚未到建设截止时间不算延期。
- 政府换人不重置满意度；GDP 本身不作为满意度加分项（避免与股市/经营重复叠加奖励）。
- 满意度进入原支持率评分时用 `(S − 50) / 50`，不得把 0～100 直接塞进原公式。

### 22.3 提前选举

- 触发：全市人口加权平均满意度严格 < 35；或某个主要群体（3 收入边际 + 4 利益边际）
  满意度严格 < 25 且该群体占人口 ≥ 20%。
- 同一条件连续 3 个**已结束游戏月**成立；全市与 7 个主要群体各有独立计数器，
  条件不满足即清零（不同群体轮流不满不能累计成同一个三个月）。
- 新任政府保护期 180 游戏日：保护期内继续记录低满意度月份，但绝不触发；
  保护结束后仍需当次月度检查满足条件才启动。
- 每个真实任期最多一次；已在竞选中不重新启动、不延后投票、不补发基础竞选资源；
  启动后满意度恢复也不取消。提前竞选仍为 30 日。
- `elections.termSeq` 含零票重选轮次，**不是**真实任期标识；真实任期只认
  `government.currentHolder.termId` / `activeTermOf`。
- 零有效票按原重选机制处理：不创建新任期、不检查建设、不叠加属性。

### 22.4 任期属性快照

- 每次真实当选生成/取得稳定 `activeTermId`（`term-<序号>`），并在任职记录保存
  `direction`、`effects` 快照、`configVersion` 与 `source ∈ {election, caretaker, migration}`。
- `app/policy.ts::activePolicyEffects` 只读当前任期 `effects`；旧任期效果整体替换、不累乘，
  连任也只生效一套倍率；已立项研发继续使用立项时快照。
- 候选人效果保持不变：A 新立项产品研发增长项 ×1.05、B 固定运营成本 ×0.95、
  C 产品单位销售成本 ×0.98（A 不是「研发速度 +10%」）。
- 机构名仍是 `BRANDING.cityStem + 管理式民主政府`；`offices` 只表达真实存在的一个最高行政职位。

### 23.3 运行时真实 AI 招商

- 科技新区最多引入 1 家真实科技 AI 公司；创建协调入口只有 `app/city-enterprises.tryCreateCityEnterprise`。

- 资金不足保留「待招商」，只在既有游戏日节点按配置间隔重试；成功后永久标记，读档不重复创建。

### 23.4 世界同步与读档碰撞

- `world.syncLayout(readonlyLayoutView)` 按稳定 ID 增量同步建筑/道路/地面/碰撞/交互与动态 `bounds`，
  不销毁重建整个 World；`app/game` 在构造、新游戏、读档与检测到 `cityLayout.revision` 变化时调用。
- 人物移动边界、位置修正与地面渲染使用同一份动态 bounds，不再用固定 `groundSize / 2`。
- 读档顺序：恢复逻辑地图 → 同步建筑实例 → 恢复原始存档 pose → 等待该布局最终碰撞就绪
  → **仅当原位置实际非法时**做一次最小必要推出（模型失败按 fallback 碰撞视为就绪）。
- 异步 GLB 回调用 `layoutRevision` + `modelGeneration` + 建筑仍在当前布局三重检查，

- 任期的 `direction` 与 `policy` 一致；`configVersion` 为当前版本时 `effects` 必须等于配置；

- 逻辑地图：版本 = 配置版本；边界合法；城区阶段不重复、基础城区唯一且 stage = -1；

- 建设：判断的 `termOrdinal` 不超过高水位；阶段在范围内；项目时长 = 30 日、

  - 每个 `stage >= 0` 的扩建城区必须反向对应一个 completed 项目与一条完成记录（不许无来源城区）；

  - `completedStages` 每个阶段必须有 completed 项目；`reservedStages` 每个阶段必须有项目。
  - 基础城区 `district-base`（stage -1）单独处理，不要求选举建设项目，且不得伪造来源项目。
  - 不要求来源任期仍在被裁剪的 `government.terms` 里，也不要求批准记录仍在展示用 `judgements` 里；
    永久关联只依赖项目、完成记录、城区与已有高水位。
  - 不一致的当前版本存档明确拒绝，错误信息指出项目 id / 城区 id；不自动补造城区、
    不释放已用阶段、不删除完成历史。

  不重建公司、不重复建设。

## 二十五、房地产与住房契约（v17）

### 25.1 切片与权威

| 数据 | 权威来源 | 说明 |

| 产权 | `realEstate.properties[*].owner` | `player` / `household:<groupId>` / `investor:<id>` |
| 入住 | `realEstate.properties[*].occupancy` | `free-residence` / `owner-occupied` / `vacant`；土地为 null |

- 永久居住权必须且只能有一处（`home-001`）：产权属于非玩家主体，`freeResidenceFor = 'player'`，
  不计入个人净资产，不产生房租，不可出售、不可出租。
- 晴川公寓固定 100 套（1 套居住权 + 99 套可售）；新区住宅按配置的单元计划交付。

### 25.2 成交与资金

- 唯一写入入口 `app/real-estate.executePurchase`，在同一份草稿里完成：
  校验资产/买卖双方/保护期/价格与版本 → 划款（`transferFunds` 或 `transferReservedFunds`）
  → 清空该资产全部报价（各自释放预留）→ 产权与入住转移 → 挂牌关闭 → 成交记录。
- 玩家买入用个人银行存款，全款支付；首版没有按揭、没有过桥贷款。
- 价格或挂牌版本与玩家确认过的不一致时 **明确拒绝**（`PRICE_CHANGED` / `LISTING_CHANGED`），
  不静默换价、不缩量、不换资产。
- 居民与 AI 在保护期内不能买入未售新住宅；玩家在保护期内可以买（保护期即玩家优先窗口）。
- 玩家持有的住宅挂牌后由月度市场匹配成交（居民与 AI 都是真实买家），
  没有保底回收、没有即时卖出；价格过高可以长期无人问津。

### 25.3 宏观居民与住房市场

- 家庭数 `= floor(阶层人数 ÷ 家庭规模)`；每月在人口月结之后同步，人口仍是唯一权威。
- 群组收入与消费是**宏观外部输入**（配置的户均金额 × 家庭数），单据 id 为
  `housing-income:<monthKey>:<groupId>` / `housing-consume:<monthKey>:<groupId>`；
  同一月份重复推进不会重复入账（先判 `housing.lastSettledMonthKey`，财务侧再判重）。
- 群组支出上限是「余额 − 预留」中的余额本身（群组没有预留）；不允许透支。
- 购买力 = min(意愿存量, 储蓄档位内可负担家庭数, 群组储蓄 ÷ 房价)，
  并要求房价 ≤ 家庭年收入 × 配置倍数；到达上限后不再成交。
- 月度成交上限：每群组 6 套、全市场 12 套（叠加在需求/资金/供给约束之上）。
- 改善置换：买新房后旧房立即释放为空置并挂牌；卖出前不产生资金流入，也不把家庭算作两套自住。
- 住房压力：`gap = clamp((房价/年收入 − 舒适倍数) ÷ 舒适倍数, −1, 1)`，
  `H = clamp(0.5 + 0.5×gap + 0.4×未满足意愿占比, 0, 1)`。

### 25.4 建设交付与统计隔离

- 住房新区完成时交付住宅单元一次（按建筑 id 幂等）；保护期从交付时刻起算 180 日。
- 住宅交付、房地产成交、估值变化与宏观储蓄注入都不登记 GDP，也不产生 GDP 财务账户。
- 土地估值可用指数、已完成建设阶段与当前执政方向修正（有界、确定性，不预知选举）；
  它是参考估值，不是成交价。

### 25.5 存档（v16 → v17）

新增 `realEstate`、`housing`、`finance.subjectAccounts` 的 `household:<id>` 账户与 6 个流水类别。

- 迁移以**迁移时刻**的阶层人数建立群组（不追溯历史增长），一次性为卖方与 AI 注入资金、
  建立晴川公寓 100 套与 4 块储备土地；
- 初始 99 套的保护期使用「开局第 7 个月月初」的绝对时刻：已过该时刻的旧档不再受保护，
  不会重新获得整段保护期；
- 已完成住房新区按真实布局补齐单元（幂等），不虚构不存在的建设；
- 不重写历史月报、不追溯退款、不追溯减免旧房租，旧生活欠款保留；
- 迁移用深克隆，同一份旧档重复解析不会重复注资或重复发房。

### 25.6 校验

- 产权主体类型合法；`household` 必须是配置中的群组，`investor` 必须有真实资金账户；
- 住宅必须有建筑 id 与合法户型，土地必须有地块 id 且不能挂牌；
- 入住状态与权利人标记一致；永久居住权恰好一处且不属于玩家；
- 晴川公寓住宅单元恰好 100 套；挂牌价不低于下限、版本 ≥ 1、挂牌时间不晚于当前时间；
- 土地报价必须指向存在的房产、出价机构有账户，且预留金额与报价金额**完全相等**；
- 成交记录 id 唯一且序号小于 `nextTradeSeq`；只有玩家作为卖方才记录已实现价差；
- 群组自有住房不超过家庭数、意愿不超过家庭数、每个群组都有资金账户；
- 日期、金额全部按非负安全整数校验；当前版本损坏字段明确拒绝，不静默补默认值。

## 房地产验收修复契约（存档 v18）

- `listingVersion` 对每项房产单调递增，当前挂牌的 `version` 必须与该高水位一致；旧版挂牌请求不能对重挂牌生效。v17 存档保留现有挂牌版本；无挂牌时初始化高水位为 0。
- 住宅市场对无法收款的卖方与 AI 可用资金不足的房源提前跳过；其它异常不得被吞掉，月度推进在同一 `GameStore.run` 中整体回滚。
- 改善置换只能由持有可追踪自住房的群组执行；旧房变为空置并按实际挂牌，资金只能在售出时入账。无具体旧房的宏观家庭保持需求，不发生改善成交。
- 人口阶层转移使用当月人口记录的流动与结算前人数，不将自然增长当作跨群组资金流。群组储蓄经 finance 以 `housing-reclassification` 记账；居住数量、意愿和具体房屋产权按同一来源比例协调。房屋、余额及收支不凭空复制。
- 群组家庭数取整为 0 时，按相邻流向优先转移剩余资金与产权；无法找到接收群组或完成划转时整次月结回滚。接收方住房容量不足时多余房屋保持产权但变为空置。

## 二十六、界面入口与现场权限

- 导航、分类跳转、待办与快捷入口都必须满足 `ENTRY_SECTIONS` 与现场要求，不能只隐藏按钮。
- `PanelManager.entry` 与 `Game.activeShopId` 只存在会话内存，关闭窗口、读档、新游戏清理；不写存档。
- 玩家现场操作在 `app/game` 提交前检查 `entry-policy`；带确认框的操作在确认后再次检查。
  入口检查不替代金额、价格、挂牌版本、股数、预留或业务权限校验，不用于 AI 与定时模拟。
- 证券中心仅有一处行情与买卖区；买卖模式只存在内存，换标的重置数量与预览价。
- 上市、融资、报价、回购与资本宣传在证券中心办理；人物治理页只绑定当前管理公司（CEO），
  并在治理回调中核对目标 companyId。其他持股公司的权利在证券中心按原业务权限办理。
- 人物界面的持仓与房地产明细只读，房地产复用 `buildEstateView(state, false).holdings`；
  K 线在证券中心，房地产买入、挂牌与报价处理在晴川公寓，原有 v18 交易确认与校验保持。
- 政治环形图使用同一视图内 12 个互斥群体的 ratio，不混入收入/利益边际，不从显示文本反算。
  内部样本、群体画像、逻辑城区与月结明细卡片移除后，原数据、统计和月结接口继续保留。

## 二十七、建筑视觉契约（已接入正式地图）

- 唯一数据流：`只读 CityLayoutView + 所属城区模板版本` → `world/buildings/layout-adapter.ts`
  → `resolveBuildingPlan` → `BuildingVisualFactory.begin` → scene 挂载并原位写 `handle.collider`。
  位置、尺寸、入口、id、districtId、interactionId、shopId、companyId、available 仍以 cityLayout 为权威，
  视觉层不得写回，也不得读写 realEstate / housing / finance。
- 工厂输入为稳定建筑 id、模板版本、风格、规划宽深高、位置、朝向与可选招牌文字；唯一尺寸解析入口为
  `resolveBuildingPlan`。视觉种子只包含建筑 id、**所属城区已存模板版本**与
  `BUILDING_VISUAL_RULES_VERSION`；不得用 `layout.revision` 或全城 `layoutVersion` 代替，匹配异常须明确诊断。
- 声明空间由输入尺寸与朝向决定；全部几何含装饰、屋顶设备与招牌须在其内。
  支持宽 8–80 m、深 8–60 m、高 5–120 m（5 m 为住房新区真实输入，按单层 + 完整女儿墙实现，
  单层建筑不摆屋顶设备）；超出范围抛 `PlanRangeError`，不静默修改规划。
- 朝向按入口主轴换算：+Z→0、-Z→π、+X→π/2、-X→-π/2；旋转 90° 时传给工厂的局部宽深**必须交换**，
  使旋转后的世界包络仍等于原规划占地。声明包络写入**现有** collider 对象的六个字段，引用不变。
- `begin()` 返回单栋句柄与 result；在途取消以 `VisualLoadCancelled` 拒绝，不取消其他楼共享加载。
  世界侧异步检查为「代次 + 布局 revision + handle 仍是当前实例 + 重算的视觉指纹」四项，
  过期成功结果立即释放；过期请求的 finally 不得扣当前代次 pending 或触发新代次就绪，
  当前代次无论成功还是明确失败都恰好结算一次。
- 资产库按贴图 URL、模型 id / 节点名及真实材质参数共享在途与结果；失败移除在途缓存，
  下次请求可重试，半成品材质释放。单栋 dispose 只释放本楼合批几何、实例与自有招牌材质、
  且不碰共享资源；工厂 dispose 统一释放资产。
- 释放只有一个入口 `releaseBuildingHandle`（删除、替换、整场销毁共用）：先释放并摘除 visual，
  再释放本楼独有的占位与标签。**禁止**把工厂产物交给正式场景的通用 `disposeObject` 遍历释放；
  `CitySceneImpl.dispose()` 必须先逐栋释放，再遍历释放场景。`World.dispose` 顺序为
  「标记失效并取消在途 → 释放场景楼体 → 销毁工厂共享资产 → renderer」。
- 旧整栋 GLB 不再是成功路径：正式场景不创建 GLTFLoader，也不按模型包围盒反算碰撞；
  `LayoutBuilding.model` / `modelScaleKey` 与 `public/assets/models/*.glb` 仅作旧存档兼容与历史资源。
  正常成功路径不得回落到旧美术；旧程序化外观只允许在加载中或明确失败时出现。
- 不以窗数/阳台数反推住房单元，不改变 interactionId；存档仍为 v18，原迁移、成交、资金预留
  与住房月结逻辑保留。
