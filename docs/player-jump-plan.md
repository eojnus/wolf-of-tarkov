# 空格跳跃功能策划案

状态：讨论草案，尚未批准实施。本文由我们共同维护；已准备 GPT Work 任务书，外部 Agent 的具体实施范围仍待架构审查。

## 目标与已确认需求

- 取消空格键原有的暂停快捷键，将空格改为人物跳跃。
- 只有人物处于可跳跃的地面状态时才能起跳；按住空格不能连续无限起跳。
- 保留 Esc 暂停菜单、手动暂停以及其他现有暂停机制和通用暂停能力。
- 人物采用真实三维碰撞和跳跃落地；保留现有移动体验，避免两套人物移动系统互相争夺位置。
- 选用 Rapier 建立物理能力，未来汽车等物体可使用同一物理引擎；本轮不实现汽车。
- 将现有场景中需要参与碰撞的其他模型纳入梳理，设计可靠的三维碰撞形状。
- 使用独立分支 `feature/player-jump-spacebar`；实施前确认工作区状态，不覆盖其他未提交修改。

## 当前工程情况

- `src/app/game.ts` 处理空格暂停，统一判断手动暂停、暂停菜单和页面隐藏；人物操作还受面板、鼠标锁定和碰撞就绪状态限制。
- `src/world/world.ts` 处理人物按键、室内外移动上下文与镜头；`src/world/player.ts` 负责人物水平移动和碰撞。
- 当前人物移动碰撞以 X/Z 平面上的障碍和边界为基础；室内外分别使用各自的碰撞集合。人物位置恢复时目前落在零高度。
- `src/ui/panels.ts` 的快捷键说明仍将 Space 标为暂停/继续。现行说明见 `docs/architecture.md` 和 `docs/contracts.md`。

## 物理系统方向：Rapier

Three.js 负责渲染，Rapier 负责碰撞、刚体与运动计算，再将结果同步到画面；它提供 JavaScript/TypeScript 接口、人物控制器和车辆控制器。车辆控制器使用刚体车身与射线轮胎，需要自行制作车辆控制、模型和手感，不能视为已经完成汽车功能。Vite 支持 WebAssembly，但实际依赖版本、初始化与打包仍需在本项目验证。

先通过小范围验证确认引擎与本项目的兼容性，再按确定的范围接入正式场景；本轮不实现未来汽车。人物可考虑使用运动学角色控制器：由游戏控制期望移动和跳跃，物理碰撞负责修正位移；它不自动受到重力，跳跃速度、重力和落地逻辑仍需接入。以后车辆可以使用动态刚体与车辆控制器，但无需在本轮创建汽车占位系统。

### 对本项目的主要影响

- 现有楼体、装饰和室内均已有碰撞数据：人物移动当前只按 X/Z 判定，部分盒体也有高度信息。需要核实每类碰撞数据能否可靠转换为三维碰撞体；尤其室内门头和天花板目前只参与相机遮挡，不能直接假设已有完整人物物理碰撞。
- 碰撞来源仍应以现有规划与场景数据为准，物理碰撞体需要随布局、室内切换、异步加载和销毁正确同步。迁移人物后应明确哪一套负责人物碰撞，避免旧二维阻挡与物理结果同时控制位置。
- 物理模拟应有稳定步长，并与经济游戏时间分离：游戏速度倍率不改变人物移动；现有暂停、后台、业务面板及读档规则需要逐项确认。低帧率下的步数上限和丢弃积压策略需验证。
- 引擎初始化、WebAssembly 加载、包体和低性能设备的运行成本需要实际验证；物理对象与资源的生命周期、读档位置修正和碰撞未就绪时的门控也需要设计。
- 是否保存未来动态物体状态属于后续设计；本轮不能预设存档升级。若真实需要变更存档格式，须按项目规则另行确认。

参考：[Three.js 物理集成说明](https://threejs.org/manual/pages/physics.html)、[Rapier 人物控制器](https://rapier.rs/docs/user_guides/javascript/character_controller/)、[Rapier 车辆控制器](https://rapier.rs/docs/user_guides/javascript/vehicle_controller/)、[Vite WebAssembly 支持](https://vite.dev/guide/features.html)。

### Rapier 如何服务人物与汽车

- 人物可用胶囊形碰撞体和运动学角色控制器：游戏给出输入、跳跃和重力产生的期望位移，控制器根据三维障碍修正并返回实际位移。落地、头顶、墙面与可站立表面都取决于正确的碰撞体和参数；角色动画、转身和跳跃手感仍由游戏负责。
- 动态物体可使用受重力和碰撞影响的刚体；未来车辆控制器以刚体车身和射线轮胎计算悬挂、驱动力与转向。车辆模型、轮胎显示和操作规则仍需要单独开发。
- 渲染仍由 Three.js 完成；物理世界与画面需要明确同步。具体采用哪一种人物刚体、物理步长和碰撞方案，应先通过小范围验证决定。

## 场景与模型的三维碰撞整理

### 目标与范围

对现有正式场景中影响人物行动的模型和结构进行清点，逐项确定三维碰撞形状、数据来源与是否可站立。目标是让人物从侧面、上方和下方接触时都与实际空间相符；是否能跳到某件家具上仍取决于其形状、高度和最终跳跃手感。纯视觉装饰是否需要阻挡需逐项判断，不因模型存在就一律生成碰撞。

| 类别 | 计划检查与整理 |
| --- | --- |
| 地面与边界 | 室外地面、室内地板和可行走范围；明确落地面及边界，避免边缘掉出或落入地板。 |
| 建筑与城市街区 | 以现有规划、建筑声明包络及装饰街区碰撞为依据，核对坐标、高度、朝向、同步与动态布局更新；不能用视觉模型反推并改变业务建筑尺寸。 |
| 室内建筑结构 | 墙、门框、门头、天花板及开口按实际通行空间整理；人物和相机遮挡的用途分别核实，确保门洞可通行且头部不会穿过实体。 |
| 家具和室内设施 | 清点床、桌椅、柜体、厨房与卫浴设施等实际存在的对象，检查尺寸、位置、可站立表面及模型视觉与碰撞是否一致。 |
| 其他街景或装饰 | 清点现有会影响行走的街景与装饰，区分实体障碍和不应阻挡的小型视觉细节，保留现有设计意图。 |

### 形状和数据原则

- 优先复用可靠的规划尺寸、位置和已有碰撞数据；简单物体优先使用盒体、胶囊或多个简单形状组合。复杂几何是否需要静态网格碰撞，应按实际对象评估，而非对所有模型自动套用。
- 分清可站立面、实体侧面、头顶阻挡和开口。简单外包盒可能封死门洞、填满家具空隙或使人物站在视觉之外；必要时分解形状或明确采用近似。
- 场景视觉与碰撞使用一致的坐标、缩放和朝向；模型替换、城区布局更新、室内进入/退出和异步加载时，碰撞体同步创建、更新和释放，避免重复、遗漏或过期碰撞。
- 摄像机遮挡、人物碰撞与交互范围各有用途，不直接把任一清单无差别复制成另一清单；迁移后人物只由一套权威移动碰撞控制。
- 避免为了未来车辆或其他业务建立空壳模块、预存对象或新的存档字段；需要真实数据格式变化时另行按项目规则确认。

### 验收方向

- 清点结果应说明每类对象的碰撞来源、形状、近似和不参与碰撞的理由，记录发现的缺口，避免静默漏掉实体。
- 按最终确定的实施范围检查地面落地、墙面阻挡、门洞通行、头顶阻挡、家具接触与可站立表面；同时检查场景切换、布局变化和读档后的碰撞同步。
- 优先代码审查和最小局部验证；不以全面自动游玩替代用户运行验收。

## 原小改动实现方向（历史比较，不作为当前方案）

1. 移除应用层的空格暂停绑定，在世界输入处理中接收一次按键触发，并沿用现有人物操作门控。
2. 在现有人物控制器中增加内存中的竖直速度与高度，按真实时间应用重力并在落地时归零；起跳时检查落地状态，忽略按键重复。
3. 跳跃参数集中放在 `src/content/config.ts`。恢复位置及室内外切换时，明确处理空中状态，避免残留速度。
4. 同步更新快捷键提示与受影响的现行说明，检查镜头和阴影在跳跃中的表现；不改变存档格式。
5. 暂停时冻结人物运动，业务面板保持原有的模拟规则；具体空中开面板的处理见下方待讨论事项。

## 待讨论与决定

- **实施范围与顺序**：先选一处验证再扩展，还是同一阶段覆盖室外和室内？碰撞清点后根据实际对象和工作量确定具体交付范围。
- **跳跃用途**：是否允许跳上或越过高度合适的家具、台阶等障碍？
- **室内限制**：现有移动碰撞并非完整三维碰撞。室内天花板和门洞的头部碰撞如何处理，或是否先限制室内跳跃？
- **手感**：跳跃高度、上升和落地时长、是否需要专门的跳跃动画，待确定；先不预设数值。
- **空中打开业务面板**：人物操作锁定但模拟继续时，是让人物继续落地，还是冻结人物直至关闭面板？
- **镜头**：跳跃时镜头是否随人物高度跟随，以及跟随程度，待确定。

- 检查室内外移动碰撞、位置恢复、面板与暂停切换；Esc 和手动暂停仍按原规则工作，空格不再切换暂停。
